## Goal

The real "switch build" mechanism (`POST /api/source/switch-build`, session-scoped via
`switch_active=False`) must make every UI surface that reflects "what build is this session
working with" — the workspace-name chip, the Resources/investigations catalog, and critically the
real dispatch `simulator_id` resolution — consistently agree. Right now at least two of those
surfaces are wrong after a real, verified switch.

## Why this is needed

Found live, mid-session, while prepping item 52's 2×2 pilot dispatch: switched this session to
`sms-ecoli @ c44b69a (build #63) [main]` via the real workspace-picker UI (the exact entry text
shown in the picker's own dropdown, which is correctly labeled). Post-switch, two real, reproduced
symptoms:

1. **The top-left workspace chip shows `v2ecoli` / `main @ c44b69a`** — commit is right, repo name
   is wrong (should say `sms-ecoli`).
2. **The Resources → "Load sources into" investigations dropdown lists what looks like v2ecoli's
   full upstream investigation catalog** (10 entries, including ones like "Colony & Microfluidic
   Phenotype Quantification", "v2ecoli Baseline Showcase", "Whole-Cell Model Comparison",
   "v2ecoli → PDMP Whole-Cell Model Reformulation") **rather than sms-ecoli's known, much smaller
   descoped subset** (confirmed via `sync_upstream.sh`'s own `descope.py` pass and the real
   `gen-readme` output used to resolve this session's own sync-PR conflicts).

**Reproduced twice, independently** — once navigating directly to the `?build=63` URL, once via
the full real click-through picker flow (button → dropdown → click the `sms-ecoli @ c44b69a
(build #63) [main]` option) — same result both times, ruling out a one-off or URL-shortcut
artifact.

**Confirmed NOT a bad build registration**: `GET /core/v1/simulator/versions` for
`database_id: 63` shows `git_repo_url: https://github.com/CovertLabEcoli/sms-ecoli`,
`git_branch: main`, `git_commit_hash: c44b69a` — genuinely, correctly sms-ecoli at the DB level.
Also confirmed the picker's own dropdown-list label generation is correct code

which is exactly what rendered in the dropdown). So the bug is specifically in what happens
**after** a build is selected, not in how builds are registered or listed.

**Real, unconfirmed hypothesis** (not verified, do not treat as root cause): `switch_build`'s
FastAPI route (`/api/source/switch-build`) deliberately passes `switch_active=False` so the switch
is per-session, not process-global (`source_build_views.py:88-151`, `lib/remote_pinned.py`'s

the chip label and/or the investigations dropdown read from the process-global `active_workspace`

**The actually load-bearing unresolved question**: whether a real dispatch submit

`simulator_id: 63`, or whether it too falls back to something stale. This was the precise next
check in progress (inspecting the real `/api/remote-run-config` network response for this session)

genuinely not yet answered, not assumed either way.

**Real consequence so far: none.** This was pure read-only UI/API inspection — no dispatch fired,
no AWS action taken, no spend. Item 52's step-3 pilot dispatch is **paused**, not cancelled,

**Possibly related, not confirmed**: may be the same bug family as items 41/48

## CORRECTION, 2026-08-17 — item 63's shared-root-cause hypothesis is REJECTED, real evidence found

Item 63's own investigation fully confirmed its root cause: `switch_build`'s materialized session
build has no `.venv` (`remote_build_source.py:152`'s `materialize_session_build` is a bare tarball
extraction, no `uv sync`), so `app.py:6169`'s `session_env.prepare(session_key, source_path)` call
(missing `managed=True`) takes the "in-place, no uv sync" fast path, `env_resolver.resolve_interpreter()`
falls through to `sys.executable` (the workbench SERVER's own interpreter), and the env-worker pool
imports that commit's composite modules under the wrong dependency versions — silently degrading to
`{}` per `discover_all_composites`'s tolerant design.

**Checked whether this item's chip-label bug goes through the same env-worker path — it does not.**
Direct read (not taken from a subagent's word — independently re-verified the decisive line myself):
`vivarium_workbench/lib/report.py:562`/`692` — `workspace_name=ws["name"]`, where `ws =
yaml.safe_load((ws_root / "workspace.yaml").read_text(...))`. A plain file read off the resolved
`ws_root`. No `env_worker_pool`/`get_pool`/`known_composite_ids` anywhere in this path. `ws_root`
itself resolves via `Depends(get_workspace)` — the SAME session-aware mechanism `/api/remote-run-config`
already uses correctly (confirmed multiple times this session) — so a correctly-materialized session
build WOULD render the correct name via this function.

**Real working theory instead** (from a scoped investigation, one piece — the actual thrown exception
— still unconfirmed): `index_shell` (`app.py:3697-3743`, backs `/` and `/index.html`) calls
`render_workspace_report(ws, ...)` on every load; its own documented fallback (`app.py:3726-3737`,
"a render failure never blocks the load — we fall back to whatever is on disk") means a render
failure for a freshly-materialized session clone would silently serve whatever `reports/index.html`
already exists inside the downloaded build artifact itself — plausibly a stale file, generated at
some earlier point in sms-ecoli's own history, never overwritten because the fresh render keeps
throwing before reaching its `write_text` step.

**Conclusion: items 54 and 63 are two separate, independently-fixable bugs, not one shared fix.**
Fixing item 63 (route `switch_build`'s materialization through the managed/`uv sync` path) will NOT
fix this item as a side effect. **Next real step for this item specifically**: reproduce the switch,
then grep the live workbench server's own stderr for `"[dashboard] / re-render failed"`
(`app.py:3731-3734`) to get the actual exception — that's the one piece static source reading can't
answer. Priority bumped to match the escalation already recorded above (was `low`/`optional: true`,
now `high`/`optional: false`) — the frontmatter had drifted behind the body's own account of Alex's
explicit escalation.

The chip label's `workspace_name` (`vivarium_workbench/lib/report.py:562`/`692`,

**No vivarium-workbench PR needed for this item.** The earlier "high priority, fix it for real"

## CORRECTION 2026-08-17 (same day) — the proposed one-line fix was WRONG; real CI caught it before
## merge; item reopens with the true, larger scope now understood

Opened sms-ecoli PR #71 (`fix/item54-workspace-name-field`, `name: v2ecoli` → `name: sms-ecoli`) per
the root cause above. **Real CI failed**: `tests/test_workspace_evaluator_discovery.py::
test_seam_discovers_report_card_axis` went from passing to `assert 'report_card_axis' in {}`.
Investigated directly rather than assuming environmental (a real, live GitHub Actions `astral-sh/
setup-uv` 429-rate-limit episode was ALSO hitting unrelated jobs the same hour, so this needed a real
check, not a pattern-match) — confirmed real and caused by this change, via the actual installed
`viva_superpowers` source:

`viva_superpowers.study_evaluator._workspace_package_slug(ws_root)` reads `workspace.yaml`'s
top-level `name` field specifically to locate this workspace's **real, on-disk build_core/evaluator
package** — `resolve_package_dir(root, name)` tries `viva_<slug>/` then falls back to legacy
`pbg_<slug>/` (dashes→underscores). The real directory here is `pbg_v2ecoli/evaluators.py` — **never
renamed during the sms-ecoli fork.** Changing `name` to `sms-ecoli` makes this resolve to a
nonexistent `pbg_sms_ecoli/`, so `load_workspace_evaluators()` silently degrades to `{}` (its own
by-design defensive behavior: "a broken workspace hook must never crash evaluation") — exactly the
empty registry the failing test caught.

**This overturns the prior "ROOT CAUSE FOUND" conclusion above.** `name: v2ecoli` is not a forgotten,
purely-cosmetic stale field — it is a real, load-bearing identifier that several real mechanisms
(at minimum `_workspace_package_slug`; also worth assuming `vivarium_workbench/lib/audit_report.py`'s
`_workspace_name()` and `catalog.py`'s `slug = ws_data.get("name")` until checked) key off of to find
this workspace's actual on-disk package. The chip showing `v2ecoli` is **accurately reflecting real,
current internal package structure** — this repo's build_core/evaluator package genuinely is still
named `v2ecoli`/`pbg_v2ecoli`, even though the git repo itself is `sms-ecoli`. That's a real, if
confusing, fact about this fork, not a bug.

**Closed sms-ecoli PR #71 unmerged**, with the full explanation on the PR itself, before it could ship
a real regression.

**What a genuine fix would actually require**: renaming the real `pbg_v2ecoli/` package directory
(and its `viva_<name>`-migration successor path) to something `sms-ecoli`-derived, updating every
internal import of it, and checking for any other repo that references it by that name — a
deliberate, cross-cutting renaming project, not a one-line data edit. Given BOJ's "optimally
lightweight, minimal correct diff" tenet, this is clearly out of proportion to what item 54 asked for
and should be scoped as its own, separate, deliberately-planned item if ever picked up — NOT bundled
into a quick fix.

**Status reverts to the still-valid, independently-confirmed earlier conclusion**: RESOLVED AS
NON-BLOCKING. Dispatch resolution (`/api/remote-run-config`) was already confirmed correct
regardless of the chip's label (see the "RESOLVED AS NON-BLOCKING" section above — unaffected by
today's correction, that check never depended on the `name` field's value). The chip/investigations-
dropdown label mismatch remains real, low-priority, and now understood to need a much bigger fix than
previously thought — left open, not chased further today.

`row["repo"] = name` unconditionally (not a fallback — the entire mechanism). Remote
