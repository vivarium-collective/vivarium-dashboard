## Goal

Item 1's real dispatch (and any future large chain-dispatch campaign) must run at real, usable
concurrency — not effectively serialized to ~1 job running at a time. Fix the root cause without
reintroducing the reliability problem that caused chain-dispatch to replace array-job dispatch in
the first place.

## Why this is needed

Found live, 2026-08-17, while monitoring item 1's real 1000×10 campaign (sim163, build 69). Real,
repeated AWS Batch snapshots across ~50 minutes showed the SUCCEEDED count climbing steadily (31 →
51 → 59) while RUNNING stayed at exactly 1 the entire time, with 999 RUNNABLE (ready, zero
dependency blockers) sitting idle. Alex, directly: "24 hours for the 999 currently runnable jobs is
unacceptable. this needs to be addressed immediately."

**Real root cause, confirmed from primary source (not inferred):**

Chain-dispatch (`viva_api.simulation.simulation_service_ray.submit_chain_dispatch_job`, backlog item
33) submits every seed's per-generation chain as individually-addressable AWS Batch **MNP**
(multi-node parallel, `num_nodes=1`) jobs. This part is a genuine, hard requirement — confirmed via
that method's own docstring (git commit `b1c1365e`, "WHY MNP, not a 'singleton array job'"): AWS
Batch array-job children cannot `dependsOn` each other, and `arrayProperties.size` has a hard floor
of 2 (no size-1 "standalone" array job exists). A true per-seed dependency chain structurally
requires each generation to be its own individually-addressable job — MNP is the only AWS Batch
primitive that provides that. **This part is correct and not in scope to change.**

The bottleneck is a SEPARATE, likely-incidental consequence: these `num_nodes=1` MNP jobs are
submitted against `smscdk-ray-mnp`, whose compute environment (`RayBatchOnDemandCE-JIbhteY8YK3VF4M9`,
defined in `sms-cdk/lib/ray-batch-stack.ts`) is bound to a **cluster placement group**
(`RayMnpPlacementGroup`, `strategy: 'cluster'`) — single-AZ, tight physical proximity, real AWS
capacity constraints on how many (especially large — `r7i.4xlarge`, 16 vCPU) instances can be
launched into it concurrently. That constraint exists for the compute environment's OTHER, genuine
use case: real multi-node Ray clusters needing low-latency inter-node networking (colony sims, per
`ray-batch-stack.ts`'s own class docstring). **A `num_nodes=1` job has no inter-node traffic at
all** — it gains nothing from the placement group and pays its full concurrency cost.

The docstring's own words on why this wasn't addressed when chain-dispatch was built: "MNP with
`num_nodes=1` is the one mechanism already proven to submit a genuinely standalone job... **reused
as-is, no new job type, no sms-cdk change**." A convenience/scope decision at the time (item 33's own
PR was about the per-seed chaining design, not compute-environment tuning), not a deliberate
"this needs the placement group" decision. The SAME docstring separately, explicitly flags a related
but DISTINCT gap — losing Spot pricing (on-demand-only) vs. the superseded array design — as "left
open for a companion sms-cdk change... not this PR's scope." That flagged gap is about **cost**, not
concurrency; this item is about **concurrency**, though a fix may address both at once (see below).

**Real, empirical evidence this is a placement-group/compute-environment effect, not an application
throttle**: no `dependsOn` edges exist between different seeds' chains (`dependsOn` on the one
RUNNING job I inspected referenced only the ParCa parent — `SEQUENTIAL`). No AWS Batch scheduling
policy is attached to the queue (`schedulingPolicyArn: null`). No account-level service quota caps
concurrent MNP jobs (checked `aws service-quotas list-service-quotas --service-code batch` directly
— nothing matches). The compute environment's own `desiredvCpus` was observed sitting at exactly
16 (one job's worth) across repeated checks, not climbing toward its `maxvCpus: 2048` ceiling —
AWS Batch's own scheduler is not even ASKING for more capacity, consistent with conservative
placement-group-aware scheduling for a resource-constrained cluster placement group.

## Real, considered alternatives (why NOT simply reverting to array jobs)

Array-job dispatch for this exact workload (`batch_baseline` sweeps) existed, worked, and was
deployed before chain-dispatch replaced it (git history: `09414aaa`, `d6abf8dd`, `e66a5e2d` — "AWS
Batch Array jobs dispatch for canonical multi-seed/multi-gen sims"). It was NOT abandoned for a
throughput or reliability reason — it was abandoned because it cannot express the per-seed,
per-generation `dependsOn` chain the current design (matching real vEcoli-private's own fully
asynchronous per-seed execution, an explicit Alex decision from item 33) requires. Reverting to
array jobs would silently regress that real, deliberately-chosen design property. **Not the fix.**

## Proposed fix, not yet built

A compute environment for standalone (`num_nodes=1`) MNP jobs specifically, WITHOUT the cluster
placement group — multi-AZ (or at least not placement-group-bound), Spot-eligible (since single-node
jobs have no inter-node traffic to protect from Spot's usual placement-group friction either). A real
`sms-cdk` change (new or modified compute environment in `ray-batch-stack.ts` or a sibling stack),
NOT a `viva-api` dispatch-logic change — the job definition and the queue/compute-environment are
already independently addressable AWS Batch resources per that file's own documented pattern
("any job definition can submit against any compatible queue, no CDK cross-stack reference needed,
just the queue's name at submit time"). Plausibly closes BOTH this item's concurrency gap AND the
docstring's separately-flagged Spot-cost gap in one change, since both stem from the same
placement-group-bound, on-demand-only compute environment.

**Real risk to manage**: this touches live AWS infrastructure the CURRENTLY RUNNING item-1 campaign
depends on (`smscdk-ray-mnp` / `RayBatchOnDemandCE-JIbhteY8YK3VF4M9`). Must not disrupt that queue —
build/test the new compute environment in isolation (a new, separate CE/queue) before repointing
anything the live campaign uses, and confirm ParCa/colony-sim genuine multi-node use cases (which DO
need the placement group) keep using the existing one unchanged.

## Status: FIXED, PR open — https://github.com/vivarium-collective/sms-cdk/pull/37

**Description**: Built, tested, and verified in an isolated worktree (`sms-cdk`, branch
`fix/item65-standalone-mnp-compute-env`). New `RayStandaloneCE` compute environment + `ray-standalone`
job queue — same instance type/vCPU ceiling as the existing MNP CE, no cluster placement group,
spans every private subnet. Reuses the existing `ray-mnp` job definition unchanged (no new job type).

**Real, decisive verification**: `cdk diff` against the LIVE `smscdk-ray-batch` stack shows this is
purely additive — 2 new resources, 2 new outputs, zero modifications/deletions to anything existing.
`smscdk-net`/`smscdk-shared` show no drift. The live 1000×10 campaign's actual queue is untouched.
9 new regression tests pass; the existing suite's pass/fail count is unchanged (1 pre-existing,
unrelated failure — a stale `arrayTaskMemoryMiB` default assertion, confirmed pre-existing against a
clean baseline, not touched here).

**Not yet done (at the time #37 was written)**: pointing chain-dispatch's real `numNodes=1`
submissions at the new `ray-standalone` queue — now DONE, see below.
