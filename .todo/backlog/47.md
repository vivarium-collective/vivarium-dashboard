## Goal

Add a dark/light mode theme switcher to vivarium-workbench's UI, informed by a feasibility
assessment of going further to a fuller selectable-themes system (multiple named themes, not
just a binary toggle).

## Why this is needed

**Investigation (2026-08-13, grounded in the real source — not assumed).** A binary light/dark
toggle **already exists and ships today** for the main SPA. This is a coverage-completion +
feasibility-decision item, not a build-from-scratch one:

- `templates/index.html.j2` has a real toggle button (`#viv-theme-toggle`,
  `onclick="_toggleTheme()"`, sun/moon icons), a no-flash-of-light bootstrap `<script>` that reads
  `localStorage.getItem('viv.theme')` and sets `data-theme` on `<html>` before first paint, and
  even a dark-specific logo swap (`data-light-src`/`data-dark-src` →
  `vivarium-logo.png`/`vivarium-logo-dark.png`).
- `_toggleTheme()` is defined in `static/walkthrough.js:2094`.
- `static/style.css` (4876 lines / 227KB) has a base `:root{ }` palette (9 custom properties:
  `--bg`, `--panel`, `--border`, `--accent`, `--accent2`, `--string`, `--num`, `--bool`, `--gray`)
  and a full `:root[data-theme="dark"]{ }` override block (from line 4482) redefining ~15 more
  tokens (`--rail`, `--surface`/`-2`/`-3`, `--field`, `--border-2`/`-faint`, `--hover`, `--active`,
  `--text`/`-muted`, `--heading`, `--link`), plus **340 total `data-theme="dark"`
  component-specific selector overrides** throughout the file.
- `templates/study-detail.html` carries the identical no-flash bootstrap script and shares the
  same `localStorage['viv.theme']` key (same-origin), so it inherits toggle state from the parent
  SPA.
- No `prefers-color-scheme` media query exists anywhere in the codebase (confirmed via
  repo-wide grep) — the system is manual-toggle-only today, defaulting to light when unset.
  Adding `prefers-color-scheme` as the *initial* default (before any manual override) would be
  small and low-risk.

**Real gaps** (why this isn't just "already done, close it"):
- `static/progress-track.css` (108 lines) and `static/snapshot-readonly.css` (179 lines) have
  **zero custom properties and zero `data-theme` overrides** — confirmed via grep.
  `study-detail.html` loads `style.css` + `progress-track.css`; the published read-only snapshot
  bundle loads `style.css` + `snapshot-readonly.css`. Toggling dark mode today likely leaves
  those elements light-colored against a dark page — an inconsistent, half-themed look.
- `static/explorer.html` has zero theme-related code at all (no toggle, no `data-theme`, no
  localStorage read) — not integrated with the rest of the app's theme system.
- `vivarium_workbench/loom/` (the vendored bigraph-loom React/Vite composite-state viewer, served
  at `/loom-explore`) is a fully separate frontend stack (its own `src/App.css`, Vite-built
  `_dist/`) with **no theme handling of its own** — confirmed via grep of its `index.html` and
  source tree. It would need entirely separate treatment (its own CSS variables / dark override,
  or stay un-themed). Scoping caveat only — not to be solved by this item.

**Deployment footprint** (grounded in the real Dockerfile, not general knowledge): the only
asset-processing step touching this repo's own `static/` and `templates/` is a plain `COPY . .`
— no minify/bundle/webpack/esbuild step. The Dockerfile's one real build step
(`scripts/build_loom.sh`) is for the *separate* vendored bigraph-loom Vite bundle, unrelated to
this repo's own vanilla CSS/JS. Static assets are plain text, copied byte-for-byte. Growing
`style.css` by a few hundred KB (more theme blocks) against an image that already bundles a full
Python 3.12 + Node 20 toolchain, Cython extensions, and a copied workspace venv is negligible
either way.

**Complexity — completing binary dark/light coverage**: small. Same pattern already proven in
production; apply it to 2 CSS files (287 lines combined) + 1 HTML file currently with zero theme
awareness. No new mechanism needed.

**Complexity — fuller selectable-themes system** (N named palettes + a picker; opencode's
`/themes` command referenced only as the *shape* of a picker-with-several-options, not as
something to inspect or copy from): architecturally a natural, low-mechanism-risk extension —
the existing `data-theme` attribute + custom-property token-swap pattern already generalizes
from 2 states to N with no new plumbing (more `:root[data-theme="X"]{ }` blocks + a picker UI
instead of a binary switch, same `localStorage` key). The real cost driver: ~340 of the existing
dark-mode rules hardcode component-specific hex values directly (e.g. `color:#c7d2fe`,
`background:#3a1518 !important`) rather than routing through `var(--token)` — so cleanly
supporting a 3rd/4th/5th theme means either (a) a one-time token-consolidation refactor of those
340 rules first, or (b) hand-authoring another ~340-rule override block per additional theme,
which does not scale and directly risks breaking existing styling.

**Recommendation**: do the small binary-coverage completion regardless (low risk, closes a real
inconsistency, same pattern already proven). Treat the fuller N-theme system as a legitimate
follow-on **only if** preceded by/bundled with the token-consolidation pass on the ~340
hardcoded dark-mode rules — without that, N-theme support is a bad trade against the "doesn't
risk breaking existing styling" condition. Deployment size/footprint is a non-issue in either
direction.
