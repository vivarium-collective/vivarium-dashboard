## Goal

Adjust the `sms-pipeline-progress` skill (`~/.claude/skills/sms-pipeline-progress/`) to support
chain-dispatch (MNP, per-seed job chains) as a first-class dispatch shape, and remove the array-job
shape if it's no longer used by anything in the ecosystem.

## Why this is needed

It is incredibly useful. Confirmed live, concretely, 2026-08-17: invoking the skill against sim165
(the real 1000×10 campaign) showed it's built entirely around the AWS Batch ARRAY-JOB shape —
`arrayProperties.statusSummary` off a single job-id representing the whole run, S3 paths sampled
per-seed under that one job. But chain-dispatch (item 33's per-seed job chains, `numNodes=1` MNP
jobs with `dependsOn` sequencing across generations) is the mechanism every real campaign has used
since viva-api 0.9.42 — there is no single job-id that represents a chain-dispatch campaign the way
an array job's parent does, so Step 1 of the skill doesn't even apply. Had to adapt the verification
methodology ad hoc, in-conversation, rather than running the skill as-is.

The skill's own SKILL.md already half-acknowledges the gap ("Analysis stage... unverified-for-this-
shape (Array-jobs parent dependency, as opposed to the already-proven MNP/single-seed path)") but
the real gap is broader than just the analysis-stage caveat — the whole per-child render model
(Steps 1, 3, and the final ASCII bar) assumes array-job semantics throughout, not just that one
stage.

**Concrete adaptation used as a live workaround this session** (a starting reference for the real
fix, not a spec): `atlantis simulation status <id>` for the coarse top-level state; the new
`GET /simulations/{id}/chain-progress` endpoint (viva-api PR #257, item 6) for real per-seed
aggregate counts (`seeds_total`/`seeds_succeeded`/`seeds_failed`/`seeds_in_progress`); direct
`aws batch list-jobs` per status against the real queue (`smscdk-ray-standalone` or
`smscdk-ray-mnp`, whichever the campaign is actually routed to) for job-level RUNNING/RUNNABLE/
SUCCEEDED/FAILED counts, using `--query 'jobSummaryList[*].jobId' --output text | wc -w` rather than
a JMESPath `length()` query.

**Two DISTINCT real manifestations of the same root pattern found this session, both worth carrying
into the fix** — `aws batch list-jobs` + a JMESPath `length()`-style counting query is unsafe in
BOTH pagination modes, not just one:
1. WITHOUT `--no-paginate` (full auto-pagination): `length(jobSummaryList[?contains(...)])` gets
   applied PER PAGE, not to the merged result — silently prints one small count per page instead of
   one aggregate (the same gotcha the skill's own Step 3 already documents for S3 listing).
2. WITH `--no-paginate`: confirmed live this session as the actual root cause of a background
   Monitor's own persistently-wrong `succeeded` counts (19/22/30 reported vs. 94/100/101 real,
   independently verified) — silently truncates to just the FIRST page (~100 results) and reports
   `length()` of only that, with zero indication anything was cut off.

Neither failure mode raises an error; both look like a normal, confident number. The safe pattern in
both cases is `--query 'jobSummaryList[*].jobId' --output text | wc -w` (or `-l`), never
`length(...)` — text output concatenates correctly across full auto-pagination, and honestly reflects
whatever was actually fetched under `--no-paginate`, in neither case pretending to be a count it
isn't.
