## Goal

Make the fully-remote workspace picker's pinned-build binding (`?build=<id>`) a persistent,
first-class part of a tab's URL/session instead of a one-shot bootstrap trigger that gets
resolved into a cookie and immediately stripped — and fix the cross-tab cookie-clobbering
correctness bug this investigation surfaced along the way.

## Why this is needed

**Origin.** Alex observed, on the real live smscdk deployment: opening a different pinned
workspace build opens a new tab; its first paint shows the stale/previous workspace (URL
`.../?build=58`, dropdown still showing the old selection); after ~10s both flip to correct,
and the URL strips down to bare `/workbench`. Two framings were investigated in parallel:
this item (persistent-URL architecture) and item 41 (existing item, UX-masking of the
transition — now enriched with today's findings, see that file).

**Verified current mechanism** (2026-08-13, grounded in real source, not assumed):
- Session identity is a browser-wide cookie, `vw_session` (`lib/session_registry.py:25`,
  HttpOnly/SameSite=Lax/path=`/`) — **not per-tab**. Real per-tab identity is a
  `sessionStorage` id sent as header `X-VW-Session` (`static/session.js:31-64`), preferred
  over the cookie by `_session_workspace_mw` (`api/app.py:610-651`) — but only on JS
  `fetch()` calls; a plain reload or typed URL carries no header, only the shared cookie.
- `?build=<id>` (a query param — real shape confirmed `/workbench/?build=58`, not a path
  segment) is parsed **client-side only**, in `session.js`'s `bootstrapSpawn()`
  (`session.js:119-136`). `GET /` (`index_shell`, `app.py:3639-3671`) resolves the workspace
  purely from `Depends(get_workspace)` → cookie/header and **never reads the query string at
  all** — confirming it's a one-shot trigger, not routed state.
- The ~10s gap is real work, not a timer: `bootstrapSpawn` POSTs `/api/source/switch-build`
  (`app.py:6054-6098` → `lib/source_build_views.py:88-151`), which runs
  `materialize_session_build`'s real per-session `shutil.copytree`
  (`lib/remote_build_source.py:152-221`, deliberately not a hardlink) plus
  `ensure_git_workspace`'s 5 sequential git subprocesses (`remote_build_source.py:224-270`).
  Cold path is documented at ~224s (`remote_build_source.py:39`), so ~10s implies a warm
  shared-cache hit — organic latency, not a hardcoded delay. On success, `session.js` strips
  the param (`stripParam()`, `138-145`) then does a full `window.location.reload()`
  (`153-157`) — not a rerender, not a server redirect.

**A real correctness bug, not just cosmetic** — found as a side effect of this
investigation, independent of whether the "persistent URL" feature below ever ships:
`_session_workspace_mw` (`api/app.py:645-653`) re-stamps the shared `vw_session` cookie to
match whichever tab's session key most recently appeared via a header-carrying fetch (this
is deliberate — it's how a stale cookie from an earlier unbound session eventually
converges). Side effect: a plain reload or typed URL on tab A, fired right after tab B makes
any fetch, picks up the cookie tab B just re-stamped — **tab A can silently start rendering
tab B's workspace**. This directly undermines an already-documented, explicit design goal —
`docs/session-binding.md` §2 states "Each browser **tab** is its own session on its own
workspace — independent" as a non-negotiable goal, and §9 discusses the shift away from
per-browser sharing. This is a gap in a stated intention, not a new ask.

**Proposed plan** — per this ecosystem's "existing pattern first" design philosophy:
- **Reuse (1), unchanged**: `session_registry`, the already-idempotent
  `materialize_build`/`materialize_session_build` (short-circuits on an existing dir,
  `remote_build_source.py:123-125,195-196`), both switch/switch-build POST endpoints.
- **Extend (2), the core fix**: (a) `bootstrapSpawn` (`session.js:138-163`) stops calling
  `stripParam()` — the `?build=` value stays in the URL permanently, with a sessionStorage
  marker so an ordinary reload skips a redundant (harmless) re-POST; (b) `index_shell` /
  `get_workspace_context` (`app.py:384-419`, `3639-3671`) learn to notice a query param the
  resolved session isn't yet bound to and render a binding placeholder instead of stale
  content — this placeholder is the same surface item 41 already wants a real loading
  animation for, so the two items should be implemented together, not independently.
  Existing precedent already in this codebase for URL-as-state: `/studies/{slug}`
  (`app.py:3758-3787`) already resolves purely from a URL segment, no cookie;
  `study-detail.js`'s `?tab=` already deep-links from a query param. This generalizes both.
- **New (3)**: none needed for the core ask — only a tab-local sessionStorage marker and a
  placeholder state, both additive to existing mechanisms.

**Complexity**: medium. Files: `static/session.js`, `api/app.py`, plus tests
(`bootstrapSpawn` isn't currently exported for Node-side testing, `session.js:165-176`).

**Explicit note**: never-stripping the param is a visible, permanent UX change — a
shared/bookmarked link now carries a pinned build. That's the intended point (open N tabs,
each independently pinned, each surviving a cookie clear), but worth Alex's explicit
sign-off before implementation, not just inferred from this write-up. The cookie-clobbering
fix has value on its own regardless of whether the full persistent-URL feature ships.
