## Real investigation, 2026-08-17 — design question ANSWERED (poll, not SSE); a working backend
## mechanism already exists but is completely unwired from the frontend; scope now precise

**Design question the item itself asked, answered with real evidence, not guessed**: SSE is NOT the
right fit for THIS deployment specifically. `viva-api/CLAUDE.md`'s own documented "Pitfall 4"
records that the Stanford ALB already flakes to `Target.Timeout` after sustained outbound traffic on
long-lived connections — introducing an SSE stream through the SAME ALB risks hitting that exact,
already-experienced failure mode. A campaign runs for minutes-to-hours; nobody needs sub-second
push updates for that. **Simple polling is the more production-grade choice for this specific
environment** — and it's also the ALREADY-ESTABLISHED pattern here: `session-status.js`
(materialization status, 2.5s interval) already proves this exact approach works, cleanly, in this
codebase. Reuse that pattern, don't introduce a new transport.

**Real, significant finding: the backend half of this may already be built and simply never wired
up.** `vivarium_workbench/lib/remote_run_views.py:533`, `remote_run_status(params)` — backs
`GET /api/remote-run-status`, does a real, on-demand status read from viva-api
(`client.simulation_status(int(sim_id))` — the SAME real endpoint `atlantis simulation status`
calls), maps it to a clean `{kind, phase, raw_status, error}` shape, and its own docstring says
outright: **"The JS panel polls this per phase."** Grepped the ENTIRE `static/`/`templates/` tree for
any reference to this endpoint (`remote-run-status`, `run-status`, `run_status`) — zero real matches.
**This endpoint is orphaned: built, real, correct — and never called by any frontend code.** This
directly matches Alex's own lived observation (dispatch a run, get a toast, then total silence) —
the toast-and-silence isn't a missing backend, it's a built backend nobody's polling.

**Real gap this doesn't close on its own**: `remote_run_status`'s granularity mirrors viva-api's
`/api/v1/simulations/{id}/status` directly — coarse (`queued`/`running`/`done`/`failed`), not the
per-seed/per-generation counts a REAL progress bar for a 1000-seed chain-dispatch campaign needs
(the numbers this whole session has been computing by hand all day via `aws batch list-jobs`
filtered by job name). A genuinely useful progress bar needs a NEW or extended viva-api-side
aggregation (a "campaign progress" summary: N succeeded / M running / K failed / J pending, out of
the total), not just relaying the single coarse status. **This is a two-repo item**: viva-api needs
the aggregation endpoint (doesn't exist yet, checked); vivarium-workbench needs (a) the wiring from
`_dispatchRemotePinned`'s "Run current spec" flow (currently fires-and-forgets, never starts any
poll) into a real progress render in the `simulate` panel (`#study-sim-table`/`#study-run-detail`,
confirmed unchanged by the recent study-spine reorg — safe to build against), and (b) extending
`remote_run_status`'s shape once viva-api's aggregation exists.

**Scope now precise, not yet built**: (1) viva-api: a campaign-progress aggregation endpoint for a
chain-dispatch `HpcRun` (real per-seed/gen counts from AWS Batch, or from DB state if it's already
tracked — check `chain_final_job_ids` first before re-deriving from raw AWS calls). (2)
vivarium-workbench: wire the dispatch flow to start polling on success, render a real progress bar
(session-status.js's polling pattern, not SSE) in the simulate panel. Not started — flagged clearly
so scope isn't lost, prioritized behind item 65 (actively blocking the live campaign right now) per
Alex's own explicit sequencing.
