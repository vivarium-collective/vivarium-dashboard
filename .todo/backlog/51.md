## Goal

`vivarium_workbench/lib/sms_api_client.py`'s `SmsApiClient.__init__` defaults `timeout: float = 30.0`,
used unconditionally by `run_simulation()`'s call into viva-api's `POST /api/v1/simulations`
(`remote_run_views.py:329`). For a canonical chain-dispatch request (`n_seeds * n_generations`
individual `SubmitJob` calls, paced ~40/s server-side inside that one synchronous request), real
observed submission time scales with campaign size — a 1000-seed x 10-generation request took
~15 minutes to finish submitting all 10,000 jobs, ~30x this client's timeout.

The result: `remote_run_submit` raises `SmsApiError(...): timed out` and the UI shows a real 500,
but viva-api itself was never told to stop — Python doesn't cancel the callee just because the
caller's HTTP client gave up — so `submit_chain_dispatch_job`'s loop keeps running server-side to
completion regardless. **The dispatch actually succeeds; the UI just reports it as a hard failure.**
This is silently misleading at exactly the scale this mechanism exists for (the real 1000x10
canonical run, item 1) — a user (or agent) seeing the 500 has every reason to believe nothing
happened and either give up or, worse, retry and create a duplicate real-money campaign.

Fix: either (a) make this specific call's timeout scale with request size (e.g.
`max(30.0, n_seeds * n_generations * 0.05)` — the observed per-job pacing overhead, with headroom),
or (b) have `remote_run_submit` return immediately (202, matching its own docstring) and poll/report
async, since the campaign is already fully tracked server-side via its own `HpcRun` row
(`chain_final_job_ids`) — this is the more correct fix, matching how the endpoint's own docstring
already claims to behave ("Returns (`{simulation_id, phase:"running"}`, 202)"), but is a bigger
change. (a) is the minimal correct fix if a quick unblock is wanted first.

## Why this is needed

Found live, 2026-08-14, during item 1's real 1000x10 baseline dispatch on smscdk: the UI reported
a 500 twice in a row (first attempt: no error even surfaced, second: a real 500), both times with
zero AWS Batch jobs created that we could see in the moment — the dispatch appeared to have failed
outright. Only checking `viva-api`'s own pod logs directly (`kubectl logs`) revealed a real
`chain-seed{N}-gen{G}` campaign actively submitting in the background, well past where the client
had already given up and reported failure. Confirmed via the real traceback:
`vivarium_workbench.lib.sms_api_client.SmsApiError: POST http://api:8000/api/v1/simulations?...
failed (sms-api unreachable — is the tunnel up?): timed out` — the error message itself is doubly
misleading (blames "is the tunnel up?", an internal-cluster call with no tunnel involved at all;
this is workbench's in-cluster call to the `api` ClusterIP service, unrelated to any SSM tunnel).

Without this fix, any future large-scale (single-digit-thousand+ total generation-cell) canonical
dispatch will hit the same false-failure UX, and — the more dangerous failure mode — invites a
well-intentioned retry that duplicates a real, expensive AWS Batch campaign, since nothing about
the failed UI state indicates the first attempt is still silently running.
