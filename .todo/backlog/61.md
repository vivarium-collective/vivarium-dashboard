## Goal

The current chain-dispatch simulation mechanism (items 33-35) only ever writes `final_state.json`
per seed — it never produces the per-generation/per-tick history data (parquet or zarr) that
`cd1_*`/`ptools_*`/`comparison_*` analysis modules actually read. Item 60's fixes made
`run_standalone_analysis.py` itself fully functional (clean imports, `"applicable"` resolution,
all deps shipped) — this is the next, deeper layer underneath it.

## Why this is needed

Directly blocks item 1 — same tier as items 55-60. Item 1's own success criterion (ecosystem
`CLAUDE.md`, verbatim) is "ENSURING THAT ALL cd1_* AND ptools_* analysis artifacts are generated as
expected." Regardless of how clean `run_standalone_analysis.py` is, it cannot produce those
artifacts if the simulation stage never writes the history data they're computed from. Firing item
1's real 1000×10 refire before this is fixed would reproduce this exact gap at full production cost.

**Q1 — is `config_data["emitter"]="xarray"` dead for chain-dispatch?** Yes, confirmed dead/vestigial.
`viva_api/simulation/simulation_service_ray.py`'s real per-generation command builder,

never calls the equivalent. `ParquetEmitter.__del__`'s finalizer (parquet_emitter.py:1355) is a
best-effort, explicitly non-blocking safety net (its own docstring), not a guarantee — consistent
with the real observed result being literally zero files, not even a partial `configuration/`
parquet.

**Q4 — the fix**: reuse the existing mechanism, don't invent one. `viva_emitters.ParquetEmitter.flush_all_in_composite`

Added `_flush_emitters()` to `run_pbg.py`, called right after `composite.run(steps)` — same
try/except-`ImportError` guard `_build_core()` already uses for every pbg-emitters import.

## REAL ROOT CAUSE FOUND, FULLY EVIDENCED, NO MOCKS — real fix implemented, PR #253 open, 2026-08-17

Second investigation returned. Root-caused for real, empirically, against a real local composite —
not source-reading theory alone, though the source reading pointed the way.

### Real local reproduction (no AWS spend) — confirms `flush_all_in_composite` was never the problem

Built the actual `v2ecoli.composites.ecoli_baseline.ecoli_baseline` composite locally (real
`process_bigraph.Composite`, real `v2ecoli.core.build_core()`, real ParCa cache already present in
`sms-ecoli-sync-item60c` checkout's `out/cache/`), ran 5 real steps, then called the REAL (not mocked)
`viva_emitters.ParquetEmitter.flush_all_in_composite(composite, success=True)` directly:

- `flush_all_in_composite` returned `1` — genuinely found and closed a real `ParquetEmitter` instance
  with real buffered data (`num_emits: 6`, `buffered_emits`: 206 real columns).
- **Zero files written anywhere under the target `out_dir`.**

This proves PR #251's flush call itself is NOT broken — the instance exists, gets found, gets closed
with real data. The bug is entirely about WHERE that instance thinks it should write.

### Real root cause: v2ecoli eagerly constructs the emitter INSIDE `to_document()`, before `run_pbg.py` ever sees the document

Traced precisely via direct inspection of the real installed `v2ecoli.composites._helpers` module
(not just `grep`, actually called the real functions and inspected real return values):

- `ecoli_baseline.py`'s `@composite_generator(emitters=[{"address": "local:ParquetEmitter",
  "config": {}, ...}])` declaration is NOT the document-level lazy address `Composite()` resolves at
  construction time — for v2ecoli composites specifically, `to_document()` calls
  `v2ecoli.composites._helpers._build_declared_emitter(decl, ...)` **during document construction**,
  which directly instantiates `ParquetEmitter(preset_config, core)` and embeds the LIVE INSTANCE into
  the returned document's `state` tree.
- `_build_declared_emitter`'s own resolution, when the declaration's `config["out_dir"]` is empty
  (always true here — the decorator declares `"config": {}`): `ws_root = _find_workspace_root(); out_dir
  = str(ws_root / ".pbg" / "parquet-runs") if ws_root else "out/parquet"`. A real compose container's
  cwd (`/app/v2ecoli`) is not a real workspace checkout, so this resolves to a path that never gets
  synced to S3 (only `RAY_OUT_DIR`/`results_dir` does).
- `run_pbg.py`'s `_redirect_emitters()` (the ONLY mechanism PR #251 or any prior fix ever touched)
  mutates the RAW DOCUMENT DICT's `config` key **after** `to_document()` already returned — but by
  then the instance already exists, already resolved, already embedded. Proved this directly: mutated
  the document's emitter-step config dict, constructed `Composite()`, and found the CONSTRUCTED
  instance's real `out_uri` attribute pointed at the ORIGINAL workspace-relative default, completely
  ignoring the mutation (confirmed via `id()` — the constructed instance's real config object is a
  DIFFERENT object than the one `_redirect_emitters()`-style mutation touched).

This is a genuinely different, deeper bug than PR #251 addressed — PR #251's flush fix is real and
necessary (confirmed: without it, even a CORRECTLY-located emitter would lose its trailing partial
batch), but insufficient alone, because the emitter was never writing to the right place to begin
with.

### The real, existing fix mechanism — v2ecoli's own documented override hook

`v2ecoli/composites/_helpers.py` has a **module-level override precedence** explicitly built for this
class of problem, real and pre-existing (not a workaround invented for this bug): `_PARQUET_EMITTER_OVERRIDE`
(set via `set_parquet_emitter_override()`) is checked with priority **before** the eager
generator-declared-default path (`_build_declared_emitter`) — matching `ecoli_baseline.py`'s own
comment: *"External overrides (`set_parquet_emitter_override`/`set_emitter_override`) still win."*
Confirmed empirically: called `set_parquet_emitter_override({"out_dir": <real target>, ...})` before
`to_document()`, and the constructed instance's `out_uri` matched exactly.

**One further real refinement needed**: the override dict is spread VERBATIM into `ParquetEmitter`'s
own config (`cfg = {'emit': ..., **parquet_override}` — confirmed by reading the exact branch) — it is
NOT run through `parquet_vecoli()`'s preset builder the way the generator-declared default is. A bare
`{"out_dir": ...}` override DID produce real output, but with **zero hive-partition columns**
(`variant`/`lineage_seed`/`generation`/`agent_id` — confirmed directly: read the real written
parquet's schema with polars, none of those 4 columns present, only the 206 real biology columns).
Since `history_files()`'s own glob (`**/history/**/*.pq`) is structure-agnostic, this wouldn't have
broken file *discovery* — but every real generation of the same seed would collide on the same
(absent) partition identity, breaking any downstream query that filters by generation/seed. Fixed by
building the override through `v2ecoli.library.emitter_presets.parquet_vecoli()` — the SAME preset
builder the eager default path itself uses — threading through the run's real `experiment_id`/`seed`
(→`lineage_seed`)/`initial_generation_index` (→`generation`), all real keys confirmed present in
`simulation_service_ray.py::_seed_generation_command`'s own `overrides` dict.

**Real end-to-end confirmation, exact production invocation shape**: ran
`PBG_CORE_BUILDER=v2ecoli.core:build_core PBG_RESULTS_DIR=<dir> python run_pbg.py --composite-id
v2ecoli.composites.ecoli_baseline.ecoli_baseline --overrides '{"cache_dir": "out/cache",
"experiment_id": "realfixtest-v2", "seed": 3, "initial_generation_index": 1}' -n 5` — real log lines
matched production exactly (`run_pbg: using workspace core from v2ecoli.core:build_core`, `run_pbg:

Real `experiment_id`, real `seed=3` as `lineage_seed`, correctly distinct partition identity.
