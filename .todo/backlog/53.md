## Goal

A real, production-grade way to cleanly cancel an in-flight chain-dispatch campaign — one API
call or one UI button, not the hand-rolled multi-step process this session had to improvise live
against real production infrastructure.

## Why this is needed

Real, live incident, 2026-08-14/15: had to stop a real 1000-seed chain-dispatch campaign
(backlog item 1) after discovering its wall-time made it unviable, then discovered (and had to
also stop) two further accidental duplicate campaigns caused by item 51's own root-cause bug
(the workbench client's 30s timeout falsely reporting failure while the real dispatch keeps
running server-side — each retry silently created a full independent campaign).

**What actually had to be done, live, with no existing tooling for it**:
1. `aws batch cancel-job` does **not** work on jobs that are PENDING due to an unmet
   `dependsOn` dependency (confirmed empirically — the API call returns success, but the job's
   status never changes, even after 20+ seconds). It **does** work on RUNNABLE jobs (dependency
   already resolved, just waiting on capacity).
2. The only reliable per-job lever for a dependency-blocked chain is `terminate-job` on whichever
   job is currently RUNNING — which, because of the architecture's own dependency-cascade design
   (a FAILED job auto-fails everything that depends on it), kills that seed's entire remaining
   chain in one call. But because the compute environment keeps promoting new PENDING(capacity)
   jobs to RUNNING as fast as capacity frees up, a single pass isn't enough — required a
   **repeated sweep loop** (list RUNNING → terminate all → wait → repeat) until real, sustained
   convergence to zero, taking dozens of iterations across a real 1000-seed campaign.
3. Even full convergence to "0 running" is **not durable** — any seed whose current job was
   RUNNABLE-but-never-yet-scheduled would resume the instant the sweep stopped. The only real,
   structural stop is disabling the **entire compute environment** (`--state DISABLED`) — a
   queue-wide lever that blocks every OTHER dispatch shape too (canonical, comparison-ensemble,
   phase0), not scoped to the one campaign being cancelled. Confirmed this blocked coworkers from
   using the fully-remote GovCloud workbench/viva-api entirely while it was in effect.
4. Re-enabling the CE after a `maxvCpus` fight (an update call that silently didn't apply — real
   value drifted to a wrong intermediate number across several attempts) required its own
   verification pass to confirm the intended capacity was actually restored, not just that the CE
   was `ENABLED`.

**None of this should require a human hand-rolling AWS Batch API calls against live production
infrastructure during an incident.** A real fix needs, at minimum: (a) a single, real
"cancel this campaign" operation — server-side, idempotent, that correctly walks a campaign's own
tracked job ids (the `HpcRun.chain_final_job_ids` mechanism already used for completion tracking)
and cancels/terminates each appropriately by its real current state, without a human needing to
know the cancel-vs-terminate distinction; (b) this exposed as a real UI affordance (a "Stop
campaign" button, mirroring the existing single-job "Stop control" already shipped for the
non-chain path — see `.todo/_backlog.md`'s own item on "Stop control to recover a frozen
in-flight run") so an operator never again needs shell access to production AWS credentials to
stop a mistaken dispatch; (c) should NOT require disabling the whole compute environment — a
correctly-implemented per-campaign cancel should never need a queue-wide blast radius.

Directly related to item 51 (the false-failure bug whose retries caused the real incident this
item is grounded in) — fixing 51 reduces how often cancellation is needed; this item makes
cancellation safe and fast when it inevitably still is.

## Status: DESIGN GROUNDED, NOT YET IMPLEMENTED

**Description**: Filed 2026-08-15, same session as the real incident that motivated it. Started
real design investigation the same day; deliberately stopped short of implementing, for a real
reason explained below — not stalled, a judgment call.

### Real design finding, verified against live data (2026-08-15)

`HpcRun.chain_final_job_ids` (`viva-api/viva_api/simulation/models.py`) tracks only each seed's
**last** generation job id, not every job in its chain. For a mid-flight campaign, that final job
is almost always still `PENDING` (blocked on its own upstream dependency) — not the job that's
actually cancellable. Verified live (not guessed) that each chain job's own `dependsOn` field
correctly points at its real predecessor:
```
chain-seed0-gen1-...  dependsOn -> chain-seed0-gen0-... (real job id, confirmed via describe-jobs)
```
This means a real cancel mechanism can walk backward from the tracked final id through each job's
own `dependsOn` link — batched `describe_jobs` calls (100 ids/call, existing
`_DESCRIBE_JOBS_MAX_BATCH` pattern already used by `get_chain_campaign_result`) — until it finds,
per seed, the one job that's actually non-terminal-and-actionable, and acts on THAT one; Batch's
own dependency-cascade (already relied on elsewhere in this design) fails everything downstream
automatically. No new DB schema needed — this reuses `chain_final_job_ids` as the walk's starting
point.

**Real, unresolved ambiguity found doing this — the reason implementation is paused, not the
reason it's stalled**: tonight's own empirical incident-response finding was that `cancel-job`
does NOT work on a job `PENDING` due to an unresolved `dependsOn` (confirmed live, real API calls,
multiple times). But AWS's own `cancel-job` documentation says it works on jobs in `PENDING` OR
`RUNNABLE` state. These aren't necessarily contradictory — `PENDING` likely covers two genuinely
different sub-cases (freshly submitted vs. blocked-on-a-dependency) that share one status string —
but nothing in `describe-jobs`'s output cleanly labels which sub-case a given `PENDING` job is in.
The safest real signal available is checking the job's OWN `dependsOn` target's status (terminal or
not) rather than trusting the `PENDING` string alone — but this needs real, live verification
against actual jobs in each state before it's trustworthy, not just reasoned through.

**Why this is deliberately not rushed**: this is exactly the tool that gets reached for during a
real, stressful incident (tonight's own). A cancel mechanism that's subtly wrong in a way that
looks like it worked (a job it can't actually act on, silently no-op'd) would be *worse* than the
current hand-rolled-but-understood sweep-loop process — it would give false confidence during
exactly the moment that confidence matters most. This needs proper implementation time with real
per-state empirical verification (submit a few tiny real test jobs in each Batch state, confirm
cancel/terminate behavior against each directly), not a rushed pass under time pressure.

### What's left to build, once real time is available

1. Verify the `PENDING` sub-case ambiguity empirically (real, tiny test jobs — cheap).
2. Implement the walk-back-and-act function in `viva-api` (`simulation_service_ray.py`, alongside
   `get_chain_campaign_result`), with real tests against each job state.
3. A real endpoint exposing it, reusing `chain_final_job_ids` — no new tracking needed.
4. A real UI "Stop campaign" button in vivarium-workbench, mirroring the existing single-job Stop
   control.
5. Should NOT require disabling the whole compute environment — the per-seed walk-back should be
   sufficient on its own; validate this holds under a real (small-scale) test campaign before
   trusting it for a real 1000-seed one.

## Step 1 (PENDING-ambiguity empirical verification) RETURNED, 2026-08-16 — hypothesis CONFIRMED and refined

Stream D (`afeec2367414893d4`) completed the cheap-verification-only task. Used `smsvpctest`'s own
Batch queue (`smsvpctest-vecoli-task-amd64`, same account/region as prod but structurally separate
from `smscdk-vecoli-task-amd64`) — never touched prod. Confirmed zero active jobs before and after;
full cleanup verified via final `describe-jobs`/`list-jobs` sweeps.

**Confirmed, more precisely than the original incident writeup**: a *sustained/observed* `PENDING`
status reliably means "blocked on an unresolved `dependsOn`." Jobs with no dependency or an
already-resolved one do NOT durably occupy `PENDING` at all — they pass through `SUBMITTED` for a
few seconds and go straight to `RUNNABLE`, skipping `PENDING` entirely (confirmed across 4
independent test jobs polled every 0.3-0.5s; `PENDING` never once observed for this case). The
distinguishing signal is exactly what this file's own design already proposed: cross-reference a
`PENDING` job's `dependsOn[].jobId` against that dependency's own current status — `statusReason`
on a blocked-PENDING job is an empty string, ruled out as a signal.

**New, operationally important refinement** (does not contradict the original incident finding,
sharpens it): `cancel-job` on a blocked-PENDING job IS accepted (`isCancelled: true` appears
immediately, API returns success) but its effect is **deferred**, not dropped — the job stays
PENDING, unaffected, for as long as the dependency stays unresolved (confirmed unchanged for 50+
continuous seconds), and only resolves to `FAILED` (using the original cancel `--reason`) the
moment the dependency itself reaches a terminal state. If the blocking dependency never resolves,
the cancellation sits dormant forever — exactly the runaway-campaign scenario this item exists for.
This directly confirms (not just theoretically, empirically) that this item's own walk-to-the-
actually-actionable-job design remains correct: relying on Batch's own dependency cascade-fail
alone is not sufficient; the walk-back function needs to find and act on whichever job is currently
RUNNABLE (cancel, takes effect within ~1 poll interval, confirmed) or RUNNING (needs `terminate-job`,
NOT `cancel-job` which is silently a no-op on RUNNING; confirmed real propagation delay of
~30-40s before a terminated job actually flips to FAILED/exitCode 137 — a real walk-back mechanism
must tolerate this, not assume immediacy).

**Caveats, honestly reported by Stream D, not rounded up**: no stable/catchable PENDING sub-case
was found for a resolved-or-absent dependency (looked across 4 jobs at 0.3-0.5s polling) — cannot
fully rule out a sub-second tick invisible to CLI polling, but not operationally relevant if so.
Did not test other hypothetical causes of sustained PENDING (fairshare throttling, malformed
resource requests, disabled queue) — out of scope. Full raw evidence (81 per-poll JSON snapshots,
full CLI transcript) left in scratchpad, not committed anywhere (verification-only, no PR/commit
per its scope).

**Status unchanged**: item 53 remains `DESIGN GROUNDED, NOT YET IMPLEMENTED` — this was verification
only, not authorization to build. The full walk-back function/endpoint/UI button remain a separate,
explicit future decision.
