2026-08-04 architecture comparison — v1 (Nextflow) vs v2 (Ray): the real structural gap found, not "Ray vs Nextflow." Full write-up: SANITY_CHECK.md (repo root).

Two parallel code-grounded research agents read v2ecoli's actual Ray dispatch path (v2ecoli/library/parallel_seeds.py, v2ecoli/workflow/{run,lineage}.py, v2ecoli/steps/batch_baseline_runner.py) and vEcoli-private's Nextflow generator (runscripts/workflow.py, runscripts/nextflow/{template,sim}.nf) to settle whether Ray itself is the wall-time problem.
Finding: the parallelism scheme is already equivalent in both systems — both fan out seeds embarrassingly in parallel (Ray tasks in v2; a Nextflow channel cross-product in v1) and both serialize generations within one lineage by biological necessity (gen N+1 needs gen N's daughter state — same forced structure in LineageProcess and in Nextflow's sim_gen_N → sim_gen_{N+1} channel chaining). "More parallelism" is not an available lever — it's already there on both sides.
The real structural difference is deployment topology, not the scheduler: v2ecoli packs ~10 seeds onto one shared, fixed 16vCPU/128GB r5.4xlarge node via Ray, where they genuinely compete for CPU/memory. vEcoli-private's default AWS Batch path gives each generation-task dedicated 1vCPU/4GB, with AWS Batch elastically scaling instance count to match runnable tasks — no shared-node contention by construction. This is a real, testable, actionable difference that doesn't require leaving Ray/process-bigraph — it's a scheduling-topology change (one dedicated small instance per seed-task via Ray's autoscaler, instead of packing many seeds onto one large node).
Also confirmed: in production, analysis is NOT inline-chained after the sim (contrary to earlier assumption) — analyses="none" is set on the sim job, and analysis is a fully separate, decoupled, manually/API-triggered K8s job run after the whole sweep lands in S3. There is no per-generation blocking-collection gate; only the final ray.get(futures) across the whole sweep.
A real, un-flagged-as-material bug was also surfaced: parallel_seeds.py's _resolve_threads = cpu_count() // n_seeds divides by total seed count, not actual seeds-per-node — already noted in v2ecoli/docs/perf/v2ecoli-vs-vecoli-performance.md as "real but unconfirmed as material" (hot path is GLPK/numba, single-threaded/GIL-bound anyway).
