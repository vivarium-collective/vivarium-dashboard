## Goal

`alembic/versions/e5a7c9d10f21_add_job_id_ext_to_compose_hpcrun.py` (viva-api, already on
`origin/main` since commit `ddcfc3b5`) adds `compose_hpcrun.job_backend` as
`NOT NULL DEFAULT 'ray'` in one step. Every `compose_hpcrun` row that existed before this migration
ran was a SLURM run (SLURM was the only compose backend before Ray support landed) — so any
pre-existing row silently got backfilled with `job_backend='ray'`, which is wrong. If anything (e.g.
a future `ComposeJobMonitor` extension) ever branches on `job_backend` to decide whether to poll AWS
Batch vs. SLURM, a legacy SLURM row mislabeled `'ray'` would get polled against the wrong backend.

## Why this is needed

Found incidentally while verifying item 61's fix — a stashed, uncommitted fix for this exact bug
was sitting in the `viva-api-item61` worktree (not mine, not part of PR #251, origin unclear —
possibly an earlier fork's tangential finding that got stashed rather than pursued or reported).
Restored safely from the stash, not lost, not yet acted on.

## Status: PENDING — real bug, impact not yet assessed, not urgent

**Not yet determined**: whether `compose_hpcrun` has any real pre-existing rows on any live database
(Stanford prod included) — if the table was empty when this migration first ran anywhere real, this
bug has had zero actual consequence so far and a simple fix to the migration file is sufficient. If
real legacy rows exist with `job_backend='ray'` that should be `'slurm'`, editing this migration's
code retroactively does nothing (Alembic tracks applied revisions by ID, not content) — the correct
fix per this repo's own Alembic conventions (`viva-api/CLAUDE.md` "Database migrations" section)
would be a NEW migration to correct existing rows, not an edit to this one.

**The stashed fix itself** (real, well-reasoned, not evaluated for full correctness yet): splits the
`ALTER TABLE` into nullable-first + backfill (`'slurm'` for existing NULL rows) + set-default-`'ray'`
+ set-NOT-NULL, so future omitted inserts still get `'ray'` (matching the ORM's own
`server_default`) while legacy rows get the correct `'slurm'`. Real diff preserved, not committed
anywhere — recoverable from this item's own investigation trail if picked up later.

**Not on item 1's critical path** — `compose_hpcrun`/the compose subsystem isn't gating anything
real yet (item 50 is its own decoupled, non-gating follow-on). Low priority, pick up whenever item
50 resumes.
