## Goal

The workbench UI must be able to configure a composite's real declared parameters (e.g.
`ecoli_baseline`'s `n_seeds`/`n_generations`) for ANY session-pinned remote build, not just whatever
build happens to already be the workbench server's own process-global default. Alex, explicit and
verbatim: "the deliverable MUST include being able to parameterize a composite!!! This is a very
basic functionality that is completely seemingly broken and/or not available at all. this is the
most fundamental thing and it cant even do that." Treated as a fundamental, deliverable-blocking
requirement, not a nice-to-have.

## Why this is needed

Found live, real, reproduced today (2026-08-17) while configuring item 1's actual 1000×10 dispatch
through the real workbench UI. The Model tab's "Runnable models" section, and the underlying
"Configure & Run" widget (`vivarium_workbench/static/configure-run.js`'s `_buildConfigForm`), both
report **"This composite takes/has no configurable parameters"** for
`v2ecoli.composites.ecoli_baseline.ecoli_baseline` — genuinely false. Item 50's own gap 1-2 work
(this same session, independently verified: real commits, real tests) already confirmed this exact
composite DOES declare both `n_seeds` and `n_generations` via its own real
`@composite_generator(parameters={...})` decorator.

**Real root cause, as far as traced today**: the parameter-discovery chain
(`vivarium_workbench/lib/composite_lookup.py`'s `known_composite_ids`/`discover_all_composites`, and
the `/api/composite-resolve` endpoint that feeds `configure-run.js`'s form-building) all run inside
the **workbench SERVER's own long-running Python process** — a persistent process that does NOT
re-import/re-install the exact commit a user has session-pinned via "switch build." It can only ever
introspect whatever `v2ecoli`/sms-ecoli is already importable in ITS OWN environment. Since
`ecoli_baseline` is a relatively new composite (introduced by v2ecoli's composite-unification
refactor, PR #373 — the same refactor already found responsible for item 61's real regression), it's
plausible the server's own baked-in environment predates it entirely, or resolves against the wrong
workspace root. **No input fields ever render for this composite's real parameters as a result — there
is currently no supported UI path to set them at all.**

**Real, live workaround used today (NOT a fix, do not treat as closing this item)**: called the
underlying `POST /api/study-baseline-add` (+ `/api/study-baseline-remove` to replace the old entry)
directly via an authenticated `fetch()` executed in the browser's own session — the exact same
mechanism the (non-rendering) "Save parameter changes" button would call — to manually write
`{n_generations: 10, n_seeds: 1000}` into the study's baseline params. This worked immediately and
was independently verified (`window._study.baseline[0].params` re-read fresh after a page reload).
**This confirms the underlying data model and save API are completely sound — only the
discovery-driven UI rendering path is broken.** The real dispatch that followed used these values
correctly (confirmed via real AWS Batch job names showing seed/generation numbers matching a
1000-seed campaign).

## Also found in the same investigation, worth reconciling separately

The live-deployed `vivarium_workbench/static/study-detail.js`'s `_dispatchRemotePinned` function is
an OLDER version than what's in the local git checkout: the live version's AWS-Batch confirm dialog
does not display `generations:`/`seeds:` lines (only repo/branch/commit/simulator id), and has no
hard "cannot dispatch without them" gate — it silently defaults to `1` via `params.n_generations || 1`
if unset. It still correctly reads real values when they ARE set (confirmed live), so this did not
cause incorrect behavior today, but it's real version drift between what's deployed and what's in the
repo, worth a normal deploy to reconcile — separate from the parameterization bug itself.

## Real user impact

This is the most basic composite-configuration workflow in the entire product (set how many
seeds/generations to run) and it has no working UI path for the composite this whole session's MVP
deliverable depends on. Every dispatch of `ecoli_baseline` at any scale currently requires either (a)
hand-crafting a direct API call the way this item's own investigation did, or (b) the CLI path
(`atlantis simulation run ...`), neither of which is an acceptable answer for a product meant to be
used by a researcher through the UI.

## Root-cause investigation STARTED, real lead found, not yet concluded — 2026-08-17

`vivarium_workbench/api/app.py:411-419`'s `get_workspace()` (the dependency `/api/composite-resolve`
and nearly every other route use, `ws: Path = Depends(get_workspace)`) is a documented **"thin shim
over `get_workspace_context(request).ws_root`"** — its own docstring explicitly says: "the routing
now flows through the per-session context, but a bound session resolves to its bound path and an
unbound one to the process default (the prior `active_workspace` root...)". **This means a real,
already-built, per-session-aware workspace resolution mechanism exists** (`get_workspace_context`,
keyed via `_session_key_of(request)` off `request.state.session_key`/`X-VW-Session` header/cookie).

**This reframes the likely bug**: it's probably NOT "no session-aware mechanism exists" (item 54's
original hypothesis) — it's more likely that either (a) "switch build" doesn't correctly *bind* the
session to the new workspace root through this same mechanism, or (b) `known_composite_ids`/
`discover_all_composites` (the actual parameter-discovery functions) don't receive/use the
correctly-resolved `ws_root` the way `/api/remote-run-config` (confirmed correct) does.

**Next real step, not yet done**: read `get_workspace_context` and `workspace_context.resolve` (the
actual per-session binding logic) directly, then trace whether "switch build" (`/api/source/switch-
build`) actually calls whatever binds a session — compare that against what `composite-resolve`
actually receives at request time. This is the precise, concrete next action for whoever (or
whichever future turn) picks this back up — don't re-discover `get_workspace` from scratch.

## THREE compounding root causes found + fixed, verified live end-to-end, 2026-08-17

Branch `fix/item63-switch-build-managed-materialization` (vivarium-workbench). Not merged — held
for Alex's review per this ecosystem's standing PR discipline. All three fixes independently
verified via REAL HTTP calls against a real materialized clone of build 69 (commit `4a08b5b`, the
exact commit item 1's live campaign runs), never mocked at the layer under test. Full real
parameters (`n_seeds`, `n_generations`, 29 others) now come back over `/api/composite-resolve` for
`v2ecoli.composites.ecoli_baseline.ecoli_baseline` for a session-bound remote build — the actual,
concrete gap this item was filed for.

**Fix 1 — `app.py:6169`, `session_env.prepare(session_key, source_path, managed=True)`.**
`source_build_views.switch_build`'s materialized session build (`remote_build_source.
materialize_session_build`) is a bare tarball/download extraction — confirmed directly from source,
no `.venv`, no `uv sync` anywhere in that path. The route previously called `session_env.prepare`
without `managed=True`, taking the "in-place, no uv sync" fast path — correct for a local dev
checkout that already has its own `.venv`, wrong for a freshly materialized remote build that has
none. `env_resolver.resolve_interpreter()` then fell through to `sys.executable` (the WORKBENCH
SERVER's own interpreter/deps), so any env-worker call for that session silently ran against the
wrong dependency versions. `managed=True` routes through the already-existing, already-tested async
`uv sync` job (`materialization_jobs.py`) — real, live-verified: `materializing → ready` in
seconds-to-low-tens-of-seconds once `uv`'s own package cache is warm (NOT the theoretical 900s
worst case — real timing observed: full `discover_all_composites` including the import cost was
~17s cold). The frontend hourglass/failure-panel UX (`session-status.js`) already exists and needed
zero changes — it activates automatically for any `managed` materialization, this flow just never
triggered it before.

**Fix 2 — `composite_resolve.py`'s `resolve_composite_for_request` routing.** Separately, and not
fixed by Fix 1 alone: this function ALWAYS routed ANY `.viv-build.json`-stamped session straight to
`SmsApiClient(...).composite_resolve(...)` — a remote sms-api endpoint the code's own comment
already documents as "added speculatively and the server side was never built." Every session-bound
materialized build hit this dead end regardless of environment correctness. Fixed by trying local
resolution FIRST when `.viv-build.json` is present (real files on disk by construction), falling
back to the remote attempt only when local misses — preserves existing behavior for a bare
deployment-wide pin (no materialized clone).

**Fix 3 — new `_local_generator_payload` helper, same file.** The "local resolution" `resolve_composite`
itself uses is a THIRD, separate mechanism from the other two: `process_bigraph.composite_spec.get`,
primed by an IN-PROCESS `discover_generators()` import (`_prime_registry`). This runs in the
workbench SERVER's own process, not the session's venv — structurally can't see a session-bound
build's generator modules, which live in that session's OWN materialized clone/dependency set. This
is exactly the anti-pattern the REST of this codebase already deliberately avoids (see
`discover_all_composites`'s own "so the HTTP process never imports `@composite_generator` modules"
docstring) — `resolve_composite`'s in-process path was simply never extended to the session-bound
case. `_local_generator_payload` reuses the ALREADY-CORRECT, already-out-of-process
`discover_all_composites` (the same mechanism Fix 1 targets) to build an equivalent payload directly
— real parameters, honest `wiring_status: "unavailable"` + notice for the state/SVG preview (which
needs a live build via `_live_generator_build`/`_live_generator_state`, has the SAME in-process-import
problem, and isn't required for a parameter config form — deliberately not also fixed here, scope
stayed to what Alex actually asked for).

**Regression tests**: `test_api_app.py::TestSourceSwitchBuildRoute::test_happy_path_repoints`
(updated — now asserts `managed=True` is actually passed, not just that `prepare()` is called at
all) + 4 new tests in `test_composite_resolve_dispatch.py` (local-first-when-found,
falls-back-to-remote-when-local-misses, the helper's own None/real-parameters cases). All pass;
`test_dispatch_deployment_prefers_local_when_generator_found` would have failed against the
pre-fix code (real regression coverage, not just green-either-way).

**Real correction to this session's own prior work, worth recording plainly**: the composite id
`v2ecoli.composites.ecoli_baseline.ecoli_baseline`, used throughout this session before today's
direct verification, IS confirmed correct — but composite ids are NOT 1:1 with file paths (a
`@composite_generator` function registers under whatever id ITS OWN decorator declares, independent
of which `.py` file it lives in — `grep`-ing for a file named `ecoli_baseline.py` and not finding one
is not proof the id is wrong). A real, if minor, verification misstep mid-investigation: briefly
concluded the id might be wrong based on a `ModuleNotFoundError` from a naive direct import,
before the REAL, authoritative check (`discover_all_composites` itself, the actual production code
path) proved it correct. Corrected within the same investigation, before reporting anything wrong
to Alex — but worth being explicit about rather than quietly smoothing over.

**Also found and fixed along the way — NOT a code bug**: item 54's real root cause (see `54.md`'s own
correction section) turned out to be sms-ecoli's own `workspace.yaml` at commit `4a08b5b` literally
declaring `name: v2ecoli`, `package_path: v2ecoli` — a stale field never updated after the fork. Zero
vivarium-workbench code change needed for that half; it's a one-line fix in sms-ecoli itself.

**Test-methodology note, for whoever re-verifies this**: live verification used a `git worktree` of
the real sms-ecoli commit to bypass an unrelated, pre-existing viva-api bug (GitHub tarball fetch
404ing for this private repo — a stale/wrong token on viva-api's own side, separate issue, not filed
here). A worktree's `.git` is a FILE pointing back at the main checkout, which `env_resolver.
_linked_worktree_main` correctly detects — meaning early verification runs accidentally borrowed the
shared sms-ecoli dev checkout's OWN `.venv` instead of exercising the real managed-materialization
path. Removing that `.git` file (matching what a real tarball-extracted materialization actually
looks like — no `.git` at all pre-`ensure_git_workspace`) was required before the verification was
trustworthy. Not a bug in the fix; a confound in how the fix was tested, caught and corrected before
concluding anything.

**Not yet done**: PR not opened (held for review, matching item 50's own standing constraint pattern
in this session). The unrelated viva-api GitHub-tarball-404 bug (blocks a FULLY clean fresh
switch-build for build 69 specifically, worked around here via the worktree) is real and worth its

## Generalization audit + real fix, before opening the PR — 2026-08-17

Alex, explicit and verbatim, before authorizing the PR: "please make sure that the fix is truly
generalized and not bespoke/customized to the mvp deliverable only. Rather, the mvp deliverable
should simply use the generalized system that any new usecases/workspaces/etc uses....that goes for
any and all of these fixes." Treated as a real gate, not a formality — audited before opening the PR,
not after.

**Audited all sibling call sites of both fixed mechanisms**, not just the one path tested:
- `session_env.prepare` has exactly one OTHER call site (`app.py:6093`, `/api/source/switch`, local
  catalog entries) — confirmed correctly DIFFERENT, not a gap: a local catalog entry already has its
  own `.venv` (real dev checkout), so `managed=False` is genuinely correct there, per the code's own
  comment ("A catalog entry is in-place local (§2a) → ready at once, no uv sync"). Fix 1 is already
  scoped to exactly the right category (materialized remote builds), not narrower or wider.
- `resolve_composite(` has exactly one other direct caller (`publish.py:941`) — confirmed correctly
  out of scope: `publish` is a CLI tool operating on an explicit local `--workspace` path, never a
  session-bound remote build (no session/request context exists for a CLI invocation).

**Found and fixed a REAL generalization gap**, though — not from the audit above, from re-examining
the fix's own coverage: `_local_generator_payload` only handles the "generator" (`@composite_generator`)
kind. A STATIC `.composite.yaml` composite under a session-bound remote build would have hit the
exact same dead end, unfixed — even though that case needs NO environment/interpreter at all (it's a
plain file read via `find_composite_path`/`CompositeSpec.from_file`). The current MVP composite
(`ecoli_baseline`) happens to be a generator, so this gap wouldn't have shown up in the campaign
Alex is running today — but it would have broken for the very first static-spec workspace to hit this
path, exactly the "bespoke to the MVP" failure mode Alex was checking for.

**Fixed by redesigning `resolve_composite_for_request` as a genuine 3-tier waterfall, reusing the
EXISTING general system at each tier instead of adding a parallel one:**
1. `resolve_composite(ws_root, spec_id, overrides)` — the SAME canonical resolution any local
   (non-remote-pinned) workspace already uses. Handles a static spec natively (environment-agnostic),
   and a generator too whenever this process's own environment happens to satisfy it.
2. `_local_generator_payload` — only reached when (1) misses; the safe, out-of-process env-worker
   fallback specifically for a generator whose module needs the SESSION's own materialized deps.
3. The existing sms-api attempt — only reached when neither general local path can see the id at all
   (the true bare-deployment-wide-pin case, or a genuinely unknown id).

**New regression test proves the fix isn't generator-only**:
`test_dispatch_deployment_resolves_static_spec_locally_no_generator_helper_needed` — a real
`.composite.yaml` under `.viv-build.json`, asserting NEITHER `_local_generator_payload` NOR
`SmsApiClient` is ever reached (raises `AssertionError` if either is called) — resolves purely
through tier 1, the same path any local workspace uses. 20 tests total in this file now, all
passing.

**Re-verified live against build 69 after the redesign** — hit a SECOND instance of the earlier
worktree-`.git` test confound (the SHARED, non-session cache base still carried the stray `.git`
file; every fresh session copy re-inherited it), which briefly made composite-resolve regress to the
old broken notice again. Root-caused immediately (not assumed away), fixed at the shared base this
time (not just one session copy), re-verified clean: 31 real parameters, `n_seeds`/`n_generations`
both present, correct new notice text. This was a second confirmation the confound is a pure
test-artifact, not a real code issue — worth recording precisely since it briefly looked like a
regression before the cause was pinned down.

**Conclusion, stated plainly**: the fix now generalizes correctly across composite kind (generator
vs. static spec) and across workspace/build identity (nothing in the code path names `ecoli_baseline`,
`sms-ecoli`, or the 1000×10 campaign) — verified by construction (the code reads generically from
`workspace.yaml`/the real registry) and by a real test proving the non-generator case specifically.
