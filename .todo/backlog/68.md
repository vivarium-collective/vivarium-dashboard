## Goal

The AWS Batch compute-environment scaling stall observed during sim166 (backlog item 1's real
1000×10 re-fire, 2026-08-17) comprehensively, holistically, and carefully scoped out and
root-caused, with a full implementation plan generated and ready for review.

## Why this is needed

Solving this would provide an answer that unblocks backlog item 1.

## What's already known — full detail in memory `item1-real-1000x10-dispatch-live.md`

sim166 (database_id 166, simulator 69, `RayStandaloneCE-VAb41EblovPbwTJQ`, `instanceTypes:
[r7i.4xlarge, r6i.4xlarge, r5.4xlarge]`, `maxVcpus: 2048`) submitted a real 1000-seed × 10-generation
chain-dispatch campaign cleanly — all 10,000 jobs landed, zero failures, real progress (24+ jobs
succeeded before the campaign was stopped) — but **never scaled past 1 real EC2 instance /
`desiredVcpus: 16`** despite ~1000 jobs sitting `RUNNABLE` (capacity-ready, dependencies clear) for
over 30 minutes.

**Ruled out, with direct evidence, not assumed**:
- CloudTrail `RunInstances` capacity errors — zero (a genuinely different signature than item 65's
  original `InsufficientInstanceCapacity` bottleneck, which this exact instance-type diversification
  fix was built to solve).
- `numNodes` misconfiguration — confirmed `1` on a real job, correctly overridden from the
  `smscdk-ray-mnp` job definition's `24` default.
- `dependsOn` blocking a specific job — the sampled job's dependency was already satisfied.
- EC2 vCPU service quota (`L-1216C47A`) — real value 2500, nowhere close to being hit.
- ECS cluster registration — healthy, the one running instance is correctly registered with a
  running task.

**The decisive, still-unexplained finding**: a complete, unfiltered CloudTrail fetch for a clean
10-minute window (well after submission finished) showed **zero scaling-related API activity of any
kind** — no `RunInstances`, no `CreateFleet`, nothing — despite the huge `RUNNABLE` backlog.
`desiredVcpus` spiked to the full `2048` ceiling exactly once, immediately after jobs first went
`RUNNABLE`, then retreated to `16` and never moved again. This reads as a genuine scaling
reconciliation stall specific to this compute environment, not a resource constraint.

**Attempted, did not work**: a benign `UpdateComputeEnvironment` nudge (re-affirming the same
`maxvCpus` value, a known community workaround for stuck Batch schedulers).

**Live hypotheses, none confirmed** — starting points for real investigation, not conclusions:
1. Something specific to the MNP job-definition shape (even at the standalone queue's `numNodes: 1`
   override) causing Batch to pace/scale MNP job launches more conservatively than equivalent
   array-job children would get. This session's own earlier chain-dispatch design notes already
   flagged "why MNP, not Array, and the cost tradeoff that leaves open" as an acknowledged open
   question — this may be exactly that surfacing at real scale for the first time.
2. Something about the EC2 Fleet/launch-template mechanism this specific compute-environment
   configuration (`ec2Configuration: [{imageType: ECS_AL2023}]`, no customer-visible Auto Scaling
   Group found under any expected name) uses under the hood, that a cleaner, more targeted CloudTrail
   or AWS-support-level investigation might reveal.
3. A transient or account-specific Batch-side issue unrelated to this session's own infra changes,
   that a fresh compute environment or simply retrying later would not reproduce.

**Real consequence right now**: item 1's own 1000×10 campaign was stopped (torn down via a manual
~9975-job termination sweep — no bulk-cancel API exists, and the AWS Batch/chain-dispatch cancel
mechanism this ecosystem needs, backlog item 53, still isn't built) specifically so this can be
root-caused properly rather than re-fire blind into the same wall. Do not re-fire the full 1000×10
campaign again until this item has either a real, confirmed answer, or a deliberate, explicit
decision to test empirically anyway (e.g. a smaller, cheaper pilot specifically designed to
reproduce or rule out the stall at lower scale/cost).
