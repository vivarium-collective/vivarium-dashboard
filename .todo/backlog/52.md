## Goal

A comprehensive, carefully scoped-out plan to get the real min/gen wall time for lineages in the
latest canonical (chain-dispatch) v2 dispatch to **less than 5 minutes**. The current real,
measured figure (~16-18.7 min/gen) is unacceptable for the MVP deliverable.

## Why this is needed

Directly related to, but a distinct escalation of, **item 46** ("v2-per-cell-wall-time-reduction",
critical, PENDING) — read that item's full history first, it is the origin of this whole thread.
Item 46 traces back to item 32 (root-caused the OLD array-jobs architecture's real wall-time gap
as AWS Batch CPU contention with no hard core cap, real v1 target = **8.66 min/gen**, derived from
sim31's own real Nextflow trace) and handed the fix to items 33/34/35 — the per-seed chain-dispatch
+ checkpoint/resume redesign that eliminated that contention problem (item 35 proved 20/20 clean
completion, zero OOM, zero contention). Item 46 itself was never updated after that redesign
landed and still just says "Acknowledged, not yet started."

**What's new today (2026-08-14/15), found live during item 1's real 1000×10 MVP dispatch**: real
per-generation-job compute time on the NEW chain-dispatch architecture (`8d50ff0`) is **16-18.7
minutes**, verified via `aws batch describe-jobs` `started`→`stopped` deltas AND via full-resolution
CloudWatch container logs for 2 independent jobs (different seeds, different generation indices).
A dedicated read-only investigation (dispatched this session) got a real phase breakdown and found:

- **Node boot + Ray cluster formation + checkpoint download + checkpoint upload + teardown:
  ~16-25 seconds total, under 3% of the real per-job time.** The per-generation-node-churn
  hypothesis (fresh node/container per generation paying real boot overhead) is **refuted by
  direct evidence** — this is NOT where the time goes, and items 33/34's chain-dispatch
  architecture itself does not need to be touched or reverted to fix this.
- **The remaining ~15-17 minutes is genuine, silent simulation compute time** — the real step loop
  actually running. This is a real, unexplained ~2x regression against the two independent prior
  baselines: sim122's own real v2 measurement (~8.78 min/gen, single continuous multi-generation
  process, older pre-chain-dispatch commit) and v1's own real production baseline (8.66 min/gen,
  sim31's Nextflow trace, item 32/46's own derived target).
- **Leading hypothesis, NOT yet confirmed**: `8d50ff0` includes item 34's checkpoint/resume
  changes, which thread real logic through the simulation's own step loop (not just at generation
  boundaries, where the investigation already showed cost is negligible) — this is the strongest,
  most specific lead, not a vague "something regressed." Explicitly NOT confirmed by diffing the
  actual commits yet — that is the single highest-value next step, named but not done by the prior
  investigation (out of its own scope).
- **Real gaps named, not yet investigated**: no commit-level diff between sim122's build and
  `8d50ff0` for the step loop; no real profiling of the ~15-17 min silent window; unknown whether
  the simulation loop can use more than one core at all (determines whether ANY hardware-based
  lever — bigger/faster instance — could help even in principle; do NOT repeat the c7i mistake
  from item 46/32's own history — a real-money instance-type experiment on an unconfirmed premise).

**The live 1000×10 campaign (item 1, experiment `sim62-sim62-api_simulation_default-ce84`) was

**Scoping agent B — RETURNED 2026-08-15, verdict: dead end, lead exhausted.**

Real, verified (not speculative): the "5.7M setFlowBounds calls" figure comes from a comment at
`v2ecoli/processes/metabolism.py:1234-1239` describing the **previous** (pre-fix) implementation.
The fix already shipped — commit `04c44b85` (2026-05-28), "perf(baseline): bit-equivalent kinetics
+ metabolism speedups (3.4%) (#89)" — confirmed via `git log -S "_prev_no_rxn_mask"`. It caches a
catalyst-presence mask and only calls `fba.setReactionFluxBounds(...)` for reactions whose mask
*changed* since the last step (catalyst presence flips for <0.1% of reactions/sec of sim time),
already using the batched array-argument form of the API — there is no unused batch API to adopt,
and no remaining redundant-call volume to cut. `fba.solve()` itself is called exactly once per step
in the real hot path (a second call exists only inside an unrelated feasibility-check helper, not a
volume issue). The commit's own measured real-world result — **3.4%** — is an order of magnitude
short of the ~50% reduction item 52 needs (17min → <5-8.7min target). Not worth further engineering
time on this specific lead.

**What agent B surfaced instead, real and still open**: the raw GLPK LP solve time itself
(`fba.solve(n_retries)`, metabolism.py:798, ~9k-reaction problem, structurally single-core) has

**Scoping agent A (per-tick step-loop overhead / XArrayEmitter) — RETURNED 2026-08-15, verdict:
real plausible lead, not confirmed, cheap to test, near-zero-code fix if confirmed.**

**The pivotal question is answered: the xarray emitter is live for the real dispatched config.**
`v2ecoli/steps/batch_baseline_runner.py:82` sets `DEFAULT_EMITTER = "both"`, threaded into
`batch_baseline.py`'s composite config, never overridden by the real chain-dispatch job. So
`LineageProcess._emit_xarray` (`lineage.py:~270-283`) is NOT dead code for this dispatch shape — it
runs on real production traffic, writing to real S3.

Call frequency: `time_step=1.0s` default, so roughly **1,500-3,000 `_emit_xarray` calls per
generation** (bounded by the 3600s `max_duration_per_gen` cap). Of the 3 things that run per call,
2 are confirmed negligible (the `mother_snapshot`/agent-diff, and `_filter_agent_state`'s shallow
dict-walk) — consistent with the original 6-agent investigation. **The real candidate is the write
path.** The xarray transducer buffers 4 ticks, then flushes; the real writer config
(`xarray_run.py:401-406`, confirmed) sets `buffers_per_chunk=1` — i.e. **zero additional batching**,
every 4-tick buffer-fill is its own real S3 zarr-chunk write, ~375-750 real S3 writes per
generation per seed. Writes run on a background thread (`ThreadPoolExecutor(max_workers=1)`), but
`AsyncBufferWriter.write()` blocks on the *previous* write's future before accepting the next
(`writer.py:467-486`) — so if a real S3 chunk-write's latency exceeds the real compute time for the
next 4 ticks, the main sim thread genuinely stalls waiting on `future.result()`.

**Honest verdict, agent's own words**: "not going to claim this explains the gap... reporting a
concrete, plausible, cheaply-testable mechanism, not a confirmed root cause." Whether the stall
actually happens depends on real S3 write latency vs. real per-tick compute time — neither has been
directly measured, only the ~15-17min/gen aggregate.

**Concrete fix, if confirmed real, requires no new code**: `buffers_per_chunk` is an *existing*
config knob (`pbg_emitters/xarray_emitter/writer.py:138-146`), already designed for exactly this
decoupling, already merges through `build_emitter_config`'s caller-override path. Raising it
(e.g. 10-25) is a config value change, not new engineering — Optimal Design Coordinate pathway 1
(existing mechanism, used as-is). Watch for an existing buffer-size=3 workaround comment
(`xarray_run.py:~484`, an `assert not include_static` edge case at exact buffer-multiple closes)
when touching this.

**Proposed validation (not yet run, zero AWS spend, zero production risk)**: instrument
`AsyncBufferWriter.write()`'s `sync()` call with real wall-clock timing; run one short local
single-generation sim twice — once against a local-filesystem zarr store (isolates compute-only
baseline), once against a real S3 bucket (isolates real write latency). Est. a few hours, entirely
local/small-scale, no AWS Batch dispatch needed. Full-fix effort if confirmed: likely under a day.
