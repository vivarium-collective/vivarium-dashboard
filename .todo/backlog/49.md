## Goal

Revise viva-api's dispatch-architecture routing decision (single-job vs. per-seed chain-dispatch)
so it's derived from the target composite's own process-bigraph-declared parameters, instead of an
ad-hoc conditional over incidental request fields.

## Why this is needed

**Origin.** While root-causing item 35's wrong-shaped first pilot dispatch (1 seed × 1 generation
instead of 2×10 — a stale-browser-state bug, unrelated to this item, already fixed), the actual
routing logic that decides AWS Batch dispatch architecture was traced to
`viva-api/viva_api/simulation/simulation_service_ray.py:964-971`:

```python
composite = getattr(config, "composite", None)
n_generations = int(config.generations or 1)
if composite is None and n_generations > 1:
    return await self.submit_chain_dispatch_job(...)
```

Alex's reaction, written to `~/sms/ecosystem/.last.md`: "That makes no sense design wise to me...
we seek process-bigraph-native design as much as humanly possible. At the heart of this entire
deliverable is process-bigraph... leveraging the design, datamodel, and overall
framework/concepts of process-bigraph itself is the semantic shared glue which binds this entire
project... theoretically-backed (based on Milner's bigraph theory)."

**Verified, not just asserted.** Three parallel investigations (theory grounding via Eran Agmon's
real published paper; an ecosystem-wide inventory of similar ad-hoc routing instances; an inventory
of existing process-bigraph-native patterns already in this codebase) plus direct source
verification confirm: the composite this code dispatches, `batch_baseline`
(`sms-ecoli/v2ecoli/composites/batch_baseline.py:66-77`), already declares `n_seeds` and
`n_generations` as real, typed parameters in its own `@composite_generator` schema. The routing
decision never consults that declaration — it re-derives the same shape by hand instead. A
same-repo, already-working precedent for consulting it exists: `viva_api/compose/run_pbg.py:169-179`
already resolves composites via `process_bigraph.composite_spec.get()`/`discover_specs()` (the
single shared registry every `@composite_generator` populates), one directory over from the
flagged code, with a docstring explicitly naming "viva-api's vEcoli ensemble endpoint" as the
intended (but not yet connected) consumer.

**Full design review, all citations, theoretical grounding, and the complete ecosystem-wide
inventory**: `viva-api/docs/DESIGN-process-bigraph-native-dispatch.md`. Not duplicated here in
full — that document is authoritative for scope/evidence; this item tracks status.

**Explicit distinction from item 46** (v2-per-cell-wall-time-reduction, priority critical,
status: root cause confirmed, real fix tracked as items 33/34/35): item 46 already investigated a
related-sounding but genuinely different question — how per-task *compute* should be physically
isolated (CPU capping, container bin-packing) — and correctly concluded process-bigraph has no
opinion on that layer. This item does not touch that finding or that layer. This item is about how
the *decision of which dispatch shape to invoke* is made, one level up — a question
process-bigraph's own composite-parameter data model does have something to say about, since the
composite already declares the shape and nothing reads it.

**Proposed plan** — per this ecosystem's "existing pattern first" design philosophy (full detail
in the docs file linked above):
- **Reuse (1), unchanged**: `process_bigraph.composite_spec.get()`/`discover_specs()` — the exact
  mechanism `run_pbg.py` already imports and depends on in the same repo. `submit_chain_dispatch_job`'s
  actual AWS Batch submission mechanism is untouched — only the routing decision changes.
- **Extend (2), the core fix**: `submit_ecoli_simulation_job`'s routing check resolves the named
  composite through the registry and reads `n_seeds`/`n_generations` off its declared `parameters`,
  in place of the current `composite is None and n_generations > 1` scalar check. Explicit
  request-level overrides still win over a composite's own declared defaults (same
  override-wins-over-default precedence `CompositeSpec._merged_params` already implements — not a
  new rule to invent).
- **New (3)**: none required for this scope. A separate, theoretically-purer direction
  (structural-delta-driven generation progression, matching `v2ecoli/steps/division.py`'s
  `_add`/`_remove` pattern) is documented in the design doc as a deliberately deferred future
  direction, not part of this item — bigger, unscoped, and adjacent to item 46's territory.

**Complexity**: small-to-medium. One routing site in `simulation_service_ray.py`, real regression
tests against the live registry (no mocking `composite_spec.get()` itself), bundled with any
version bump per viva-api's own release protocol (`viva-api/CLAUDE.md`).

**Revision, 2026-08-14**: an earlier draft additionally proposed a generic `overrides` passthrough
on `/api/v1/simulations` itself — withdrawn after verifying against `viva-api/docs/PRE-DEMO-PLAN.md`
that this endpoint is deliberately kept as the vEcoli-specific specialization, distinct from the
already-real, already-partially-built generic path (`/compose/v1/*`, `ComposeSimulationServiceRay`,
generic `run_pbg.py`) that already exists for "any composite, any domain" access. Full detail in
the design doc's own "Revision" section. This item's core scope (the routing-decision fix) is
unaffected.

**MAJOR SCOPE EXPANSION, 2026-08-14**: Alex confirmed `/api/v1/simulations` is back-compat only —
the canonical fully-remote dispatch must actually run through `/compose/v1/*`. This item's original
scope (the routing-decision fix inside the legacy endpoint) is now secondary to a much larger,
fully-scoped migration: generalizing the hand-rolled AWS Batch chain-dispatch into the compose
subsystem. Full design, evidence, and a real two-path fork (Path A: generalize the existing chain
vs. Path B: route through viva-api's already-live Nextflow-on-Batch backend) written up in the
design doc's "MAJOR SCOPE EXPANSION" section — Path A recommended. Awaiting Alex's decision.
