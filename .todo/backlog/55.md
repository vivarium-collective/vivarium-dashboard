## Goal

`viva_api.simulation.simulation_service_ray.V2ECOLI_BATCH_BASELINE_COMPOSITE_ID`
must always point at a composite id that genuinely exists in the deployed
sms-ecoli simulator image, so a real chain-dispatch (any seeds x generations >1
dispatch — the canonical batch_baseline sweep, item 1's own 1000x10 MVP shape)
does not fail at generation 0 with "no composite registered."

## Why this is needed

Discovered live, 2026-08-16, firing item 52's own pilot validation dispatch (sim
152, `atlantis simulation run item52-pilot-2x2-cli 63 --seeds 2 --generations 2
--run-parca`, per Alex's AFK/CLI authorization for item 52). The dispatch
appeared to run for ~16.5 minutes (RUNNING) then hit a real terminal `FAILED`:
`"chain dispatch: zero seed chains succeeded"`.

**Root-caused via real AWS Batch job state + CloudWatch logs, not assumed:**
both `chain-seed0-gen0-sim63-item52-pilot-2x2-cli-59f7-*` and
`chain-seed1-gen0-...` failed identically (exit code 1, "Essential container in
task exited"). The real container log (log group
`smscdk-ray-batch-RayBatchLogs2D18AAFC-8GHBqANaZjIm`, found only after the
default `/aws/batch/job` group came up empty — the MNP job definition configures
a custom `awslogs-group`) shows the exact real error:

```
run_pbg: using workspace core from v2ecoli.core:build_core
run_pbg: no composite registered as 'v2ecoli.composites.batch_baseline.batch_baseline'
```

**This is the SAME "composite not found in registry" warning seen earlier in
the workbench UI** while configuring this pilot's study (dismissed at the time
as an unrelated red herring next to the native-`confirm()`-dialog mystery — it
was real and load-bearing all along, just not chased down then).

**Full real chain of causation, verified against actual git history in both
repos (never assumed, never taken from a stale local checkout on the wrong
branch):**

1. v2ecoli's own upstream (commit `2dfeeeb97`, PR #373, "Unify composites into
   baseline: knockouts + media + batch (n_seeds)", 2026-07-25, author Eran
   Agmon) deleted `composites/batch_baseline.py` and folded its batch/lineage
   behavior directly into `composites/ecoli_baseline.py`'s `baseline()`
   function — `n_seeds`/`n_generations` > 1 now switches `baseline()` into what
   used to be the standalone `batch_baseline` composite.
2. `v2ecoli/composites/__init__.py` deliberately registers **no legacy-id
   alias** for the old name, by explicit design: *"a stale `baseline` id
   resolving silently would only hide a missed reference."* — i.e. the authors
   wanted exactly this kind of drift to fail loudly, not silently.
3. sms-ecoli hadn't synced that specific v2ecoli change until **this session's
   own PR #56** (`c44b69a1`, "sync: bring sms-ecoli up to date with v2ecoli
   (2026-08-16)") — the same sync that carried item 52's wall-time fix. The
   sync correctly, faithfully brought in everything accumulated upstream since
   the last sync (`7b0791a2`/`8d50ff07`, which build 62/item 1's real 1000x10
   campaign used) — including this unrelated refactor riding along.
4. Nothing on the viva-api dispatch side was updated — `V2ECOLI_BATCH_BASELINE_COMPOSITE_ID`
   still pointed at the now-deleted module, so every real dispatch against
   build 63 (or any future sms-ecoli build built after this point) fails
   identically and immediately at generation 0, for both seeds, every time.

**Historical near-miss worth naming**: `simulation_service_ray.py` already
carried a detailed comment from a 2026-08-06 incident where someone correctly
guessed the WRONG thing at the time — `v2ecoli.composites.ecoli_baseline.ecoli_baseline`
— because sms-ecoli hadn't synced the refactor yet then (verified: "ecoli_baseline"
had zero matches anywhere in sms-ecoli at that day's deployed commit). That
comment's own stated methodology — verify directly against the deployed image's
real commit via `git show`/`git grep`, never the separately-diverged local
v2ecoli checkout — is exactly what caught this correctly this time, now that the
sync has actually landed.

## Fix implemented, 2026-08-16 — viva-api branch `fix/item55-stale-batch-baseline-composite-id`

Per the Optimal Design Coordinates 4-question framework: question 1 answered
yes — `v2ecoli.composites.ecoli_baseline.ecoli_baseline` already exists, already
registered, already supports the exact batch/lineage shape needed (checked its
real full signature directly against the deployed commit). No new code needed
in v2ecoli/sms-ecoli; the fix is entirely on the viva-api caller side:

1. `V2ECOLI_BATCH_BASELINE_COMPOSITE_ID`: `"v2ecoli.composites.batch_baseline.batch_baseline"`
   -> `"v2ecoli.composites.ecoli_baseline.ecoli_baseline"`.
2. `_seed_generation_command`'s overrides dict: `"base_seed"` -> `"seed"` — a
   SECOND real incompatibility found by reading `baseline()`'s full signature
   directly (a strict superset of the old params except this one rename); a
   naive constant-only swap would have failed again on the very next attempt
   with an unexpected-keyword-argument TypeError.
3. Updated every now-stale comment in `simulation_service_ray.py` referencing
   the old module/registration (kept the real 2026-08-06 incident history
   intact — historical, not rewritten).
4. Updated the 5 real tests that had encoded the stale id/key as their own
   oracle (`test_ray_backend.py` — 2 composite-id string assertions, 3
   `base_seed`-keyed assertions across `TestSeedGenerationCommand` and
   `TestChainDispatchSubmission`) — these previously would have kept passing
   regardless of whether the real string was right, a textbook instance of the
   green-mock-as-go-signal anti-pattern the fix also corrects.
5. Version bump `0.9.43` -> `0.9.44` (viva-api's own release-protocol
   convention), detailed changelog entry in `version.py`.

Full real test suite: 67/67 in the directly-affected file, full repo suite run
