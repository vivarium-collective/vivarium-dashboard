## Goal

A drastic reduction/improvement of min/gen wall time for lineages when running v2 cannonical 
dispatches to match and/or exceed (in a good way) that of the cd1 v1 runs.

## Why this is needed

This represents a proactive mitigation of the wall time slowdown at the single cell level 
for v2-based canonical dispatches (multiseed x multigeneration) to match more closely the 
highly optimized and engineered wall time of v1 (vEcoli-private, which uses nextflow.)

    **Current v2 state, for comparison** (sim140, item 29's Array-jobs validation, 30×10, still
    in flight as of this writing): **22.7 min/gen — 2.6× slower**, derived from real S3

    contention (shared cache/memory-bandwidth/EBS-IOPS across many concurrent heavy sim
    processes per host) is the leading hypothesis, but not yet confirmed as the actual cause —
    v1's SLURM-dedicated-allocation-per-task model never had to share a host this way, so this
    isn't a clean isolated variable yet either.

    **ROOT CAUSE CONFIRMED, 2026-08-08 — all three investigation threads complete.** Alex's
    required deliverable (a real causal explanation, not just the quantified gap) is met with
    measured evidence, not a hypothesis:

    - **The actual cause: no hard CPU cap on AWS Batch array containers, real measured
      contention.** `docker inspect` on live sim140 containers: `NanoCpus=0, CpuQuota=0` — no
      enforced limit, only a soft `CpuShares` priority. `nproc` inside a container returns 96
      (the full host), not the reserved 2. Real `docker stats`: containers actually using
      **582%-1362% CPU** — 6-14 cores each, not 2. AWS Batch's vCPU request is a
      scheduling/placement hint, not a runtime cap. Compounded by a real, previously-unknown
      mass Spot-reclamation event mid-run that forced most of the fleet to restart and re-pack
      unevenly (11 of ~27 survivors landed on ONE host). v1/SLURM never had this problem —
      cgroup CPU enforcement gives every task an exclusive core by construction.
    - **NOT inline per-generation analysis** — an earlier note in this item (and in the
      `ray-vs-batch-array-jobs-investigation` memory) wrongly claimed per-seed `ptools_*`
      analysis runs inline per generation. RETRACTED 2026-08-08, verified false by direct source
      read (`batch_baseline_runner.py`/`workflow/run.py`): analysis runs exactly once, in a
      single post-sim flush, after the full sweep — architecturally identical to v1. The
      per-generation-named output files are just that one flush's own output granularity, not
      evidence of repeated execution.
    - **NOT more computation than v1** — direct process/config diff (Thread A) found v1 and v2
      architecturally equivalent per generation (same ~29 processes, same partitioned execution
      pattern, same 1.0s timestep). Eran's "~2min/cell" claim traces to an unrelated local
      colony-model benchmark (`v2ecoli-colony`), not the production `batch_baseline` path — not
      a real comparison to what's being measured here.
    - **Memory sizing is genuinely two-sided**: real RSS measured at 2.79-7.40GB (9-23% of the
      32GB reservation) for most children — over-provisioned on average, matching v1's ~2GB —
      but 3 sampled children still hit real OOM near gen 9-10 even at 32GB, under contention on
      the most-packed host. Sizing and CPU-capping need fixing together, not sizing alone.
    - **AWS ParallelCluster ruled out, independently confirmed why**: `sms-cdk/docs/
      remove-pcs-fsx-plan.md` documents this ecosystem already built and removed AWS PCS
      (managed Slurm-on-AWS) + FSx for Lustre in favor of Batch, for cost/complexity reasons,
      2026-04-12 — real, on-record history, not just Alex's stated preference.

    **Real fix candidates, evidence-ranked (feasibility-only, nothing built yet)**:
    1. **Individual per-task AWS Batch jobs, matching v1's exact mechanism** — top rank, reuses
       existing queue/CE entirely, `_ensure_array_job_def` already builds the right job-def
       type. Real complication: `dependsOn` caps at 20 IDs, so the analysis job needs a polling
       fan-in instead of one collapsed parent dependency (an existing pattern elsewhere in this
       codebase already does this for SLURM).
    2. **Resize + explicitly CPU-cap Array jobs, keep the mechanism** — cheapest option, but per
       the contention finding above, resizing memory alone won't fix it; the CPU cap needs
       fixing too (check whether AWS Batch/ECS exposes a hard-limit knob beyond `vCPU:` request).
    3. Kubernetes Jobs on existing EKS (real infra reuse, but zero pod-anti-affinity precedent
       to build from) and KubeRay ("documented aspiration only" in sms-cdk) — credible
       fallbacks, not first choices.

    process-bigraph confirmed to have no opinion on this layer (its own native distributed
    execution, `process_bigraph/protocols/ray.py`+`ec2_ssm.py`, is real and GovCloud-aware but
    solves a different problem — actor-pooling *within* one composite, not this outer per-seed
    fan-out) — "process-bigraph-native" isn't a coherent category for the fix, by design not gap.
