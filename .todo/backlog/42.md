## Goal

Expand `sms-ecoli`'s `ROW_BUILDERS` dict (`scripts/run_standalone_analysis.py`) to cover the
`single` and `multigeneration` analysis scales, not just `multiseed`.

## Why this is needed

Found 2026-08-12 while re-validating item 38's fix via sim 142 (2x10 baseline dispatch, smscdk).
The dispatch's own `_manifest.json` reports `status: "partial"` with two real errors:

```json
{"scale": "single", "error": "no row builder for scale 'single'"}
{"scale": "multigeneration", "error": "no row builder for scale 'multigeneration'"}
```

## Root cause (already found, not yet fixed)

`scripts/run_standalone_analysis.py:266-269` looks up a builder function per scale from
`ROW_BUILDERS` (line 131-133), which has exactly one entry: `{"multiseed": build_multiseed_rows}`.
It has had only this one entry since its introduction (commit `94551691`, "Add v2ecoli-native
standalone analysis entrypoint #24", Jul 30), unchanged across every later touch to the file
(`a549095f`, `791da69f`, `31b58162`/#38 Aug 7, `dde54a5c` Aug 11). Any `AnalysisStep`-family module
requested at `single` or `multigeneration` scale hits this gap — not a key-mismatch, the scale
strings match exactly, coverage is just genuinely incomplete. Documented as a known scope limit in
the script's own docstring; explicitly asserted by `tests/test_standalone_analysis.py:114,205,215`.

## Severity — low, not blocking anything

Does NOT affect the `cd1_*`/`ptools_*` omics deliverables (the actual canonical-workflow
requirement) — those are a separate `Analysis`/DuckDB-family class, routed through
`run_duckdb_analyses()`, called unconditionally *before* the row-builder check, untouched by this
gap. The only 2 casualties are small built-in summaries: `mass_fraction_summary` (single scale) and
`mass_growth_across_generations` (multigeneration scale).

## Scope of the fix

Add row-builder functions for the `single` and `multigeneration` scales (mirroring
`build_multiseed_rows`'s own shape) and register them in `ROW_BUILDERS`. Update
`tests/test_standalone_analysis.py`'s existing assertions (lines 114, 205, 215) — these currently
assert the single-entry-only behavior as expected, encoding today's gap as intentional, so they
need updating alongside the fix rather than left in place (or the new coverage will look like it's
failing its own regression tests).
