## Goal

Fix a cross-repo contract mismatch: viva-api's chain-dispatch analysis auto-trigger
(`simulation_service_ray.py`) emits `--n-generations <N>` to `run_standalone_analysis.py` when
`modules="applicable"`, but the actual v2ecoli/sms-ecoli script (as of sms-ecoli `main`@`0c77a10`)
does not define that argument, so the analysis job dies immediately with
`error: unrecognized arguments: --n-generations 2`.

## Why this is needed

Discovered 2026-08-16 as pilot 5's (item 52's validation pilot) auto-triggered analysis stage. The
simulation stage itself fully succeeded (both seeds wrote real `final_state.json`, all 4 chain jobs
completed in ~62-67s — this does NOT affect item 52's already-validated wall-time claim), but the
downstream analysis never produces real output.

**This directly blocks item 1, on the same tier items 55-58 blocked item 52 — corrected 2026-08-16
after initially under-prioritizing it.** Item 1's own goal statement (ecosystem `CLAUDE.md`, verbatim)
is: "ENSURING THAT ALL cd1_* AND ptools_* analysis artifacts are generated as expected... ALL
TRIGGERED ONLY THROUGH THE FULLY REMOTE smscdk AWS GOVCLOUD DEPLOYMENT." This bug means the fully
remote canonical workflow currently CANNOT produce those artifacts reproducibly — the analysis stage
dies on every `modules="applicable"` dispatch, which is the default shape for auto-triggered
chain-dispatch analyses. Not a nice-to-have to fix later; item 1 is not meaningfully progressable
without this fixed, same as it wasn't meaningfully progressable through items 55-58.

### The construction site — a self-documented, deliberate design that assumed a not-yet-landed change

`viva_api/simulation/simulation_service_ray.py:743-749` (`_build_analysis_command` or equivalent):

```python
# --n-generations exists only to let the image resolve the "applicable"
# keyword; an explicit module mapping doesn't need it. Emitting it only in
# the keyword case keeps the explicit path runnable against ANY image that
# already ships the script, so a simulator built before the keyword landed
# still gets its configured analyses instead of dying on an unrecognized
# argument. Only the keyword default requires the newer image.
gens = f" --n-generations {int(n_generations)}" if isinstance(modules, str) else ""
```

This comment explicitly names and defends against the EXACT failure mode now happening — the author
anticipated a v2ecoli/sms-ecoli-side change ("the keyword landed") that would add `--n-generations`
support, specifically to resolve `modules="applicable"` into a concrete analysis set. That change was
never actually implemented on the v2ecoli/sms-ecoli side (confirmed directly against real deployed
source, not assumed) — so viva-api is unconditionally hitting the exact "simulator built before the
keyword landed" case its own comment describes, on every `modules="applicable"` dispatch (the default
for auto-triggered chain-dispatch analyses — see `analysis_options: {"multiseed": {}}`-shaped configs
threading through as the string keyword).

### Resolved: which side changes, and why — v2ecoli-only, reusing existing logic

Read the full `run_standalone_analysis.py` source directly: it has ZERO handling of the `"applicable"`
keyword at all — `--modules` is always `json.loads()`'d, which would itself raise on a bare
`"applicable"` string even if `--n-generations` were accepted. viva-api's assumption was never
implemented on the v2ecoli side, at any point.

The fix reuses `v2ecoli/steps/batch_baseline_runner.py`'s existing `build_analysis_options()` /
`applicable_analysis_scales()` — the SAME resolution the composite's own inline flush already uses —
rather than inventing new logic or duplicating it inside viva-api (which doesn't have v2ecoli
importable anyway). This is v2ecoli-only; **zero viva-api changes needed** — it already emits the
right CLI shape (`--n-seeds`, `--n-generations`, `--modules applicable`), it was just never consumable.
