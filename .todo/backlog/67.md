## Goal

Fix the Source panel's Branch dropdown under Remote scope so a new branch (one with no existing
build yet) can actually be selected from the UI — right now it only lists branches that already
have at least one registered build, so there is no discoverable way to pick a brand-new branch
without leaving the UI entirely.

## Why this is needed

Reported by Chris Long (cplong), an important MVP-project coworker, verbatim:

> The Source panel's Branch dropdown under Remote scope only lists branches that already have
> builds — so there's no way to select a new branch from the UI. `POST /core/v1/simulator/upload`
> takes an arbitrary triple, so I can register directly, but wanted to check first.

Chris found a real, working API-level bypass (`POST /core/v1/simulator/upload` accepts an arbitrary
`(repo, branch, commit)` triple, unconstrained by what's already built) — meaning the underlying
capability already exists, this is specifically a **UI-discoverability gap**: the picker's own
Branch dropdown appears to only populate from already-registered builds, not from the real list of
branches a repo actually has. Filed as `critical` per standing instruction to thoroughly address
Chris's feedback given his importance to this MVP deliverable, and because it silently pushes anyone
who doesn't already know the raw API exists toward believing new-branch dispatch isn't possible at
all from the UI.

**Not yet scoped against real source** — filed directly from Chris's report to get it tracked
promptly; a background investigation is in flight (see session notes) to identify the actual
picker/dropdown code path (likely `static/workspace-picker.js` or a sibling Source-panel JS file,
plus whatever `lib/`/`api/app.py` endpoint currently backs the Remote-scope branch list) and propose
a concrete, minimal fix — most likely: the dropdown's data source needs to include real branches
from the repo (e.g. via a GitHub branches-list call, or reusing whatever powers a similar "pick any
branch" affordance elsewhere in this codebase) rather than being limited to already-built ones.
Findings to be appended here once back, per this backlog's own established convention (see item 54
for the pattern) of appending real-source-verified findings rather than asserting them upfront.

## ROOT CAUSE FOUND + FIXED, PR opened, 2026-08-17

**Real root cause**: `static/branch-source.js`'s Branch `<select>` under Remote scope is populated
only from `state.entries`, itself sourced exclusively from `GET /api/source/builds` (i.e., already-
registered builds). The "Build via sms-api" button — the one UI affordance actually meant to
register a *new* branch — was gated on `state.selected.repo_url`, which can only ever be set from
an already-built entry. Self-contradictory: the one path meant to solve this problem could never
actually be used for it.

**Confirmed no backend change needed**, by tracing the full call chain across both repos before
touching anything: `POST /api/source/build-remote` → `source_build_views.build_remote()` →
`SmsApiClient.latest_simulator()` → viva-api's `GET /core/v1/simulator/latest` →
`fetch_latest_commit_hash()` — a real, live GitHub API call, independent of any prior registration.
`register_simulator()` already wraps `POST /core/v1/simulator/upload`, the exact same endpoint Chris
used manually as his workaround.

**Fix** (frontend-only, `vivarium_workbench/static/branch-source.js`): a "+ New branch…" sentinel
reveals a free-text branch input (state updates without a full re-render, to preserve keystroke
focus — caught and fixed a stuck-disabled-button bug in the first draft before it shipped); the
Build button's `repo_url` now derives from the selected repo (`inRepo[0]`) rather than
`state.selected`, so it correctly enables for a typed, unbuilt branch too.

**Tests**: added `test_branch_source_js_new_branch_registration_wired` to
`tests/test_source_branch.py`, matching this file's own established string-presence-assertion
convention for this bundler-less JS file (no JS test runner exists in this repo — confirmed by
searching, not assumed). 13/13 passing (12 pre-existing + 1 new). `node --check` clean.

**Not done**: a live browser click-through — no fake/reachable sms-api backend was worth standing up
for a fix this scoped; a precise 6-step manual-QA script is in the PR instead of silently skipping
verification.
