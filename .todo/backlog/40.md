## Goal

Find the actual `jobstatusdb` Postgres enum definition (Alembic migration or `tables_orm.py`) and 
the exact string the cancel handler writes; either the enum needs a real `CANCELLED` (or whatever value) migration, or the
handler needs to write whatever value the enum actually has (e.g. `CANCELED`/`FAILED`).

## Why this is needed

`POST /api/v1/simulations/{id}/cancel` writes an invalid Postgres enum value — real 500, cancel doesn't take effect via the app:

**Found 2026-08-11/12**, same session as item 39, while cancelling the misconfigured sim 141
above. Real error returned: `(sqlalchemy.dialects.postgresql.asyncpg.Error)
InvalidTextRepresentationError: invalid input value for enum jobstatusdb: "CANCELLED"`
(`UPDATE hpcrun SET status=$1::jobstatusdb WHERE hpcrun.id=$2`, `params: ('CANCELLED', 205)`)
— the app tries to write a status string the DB's own `jobstatusdb` enum type doesn't
contain (likely a naming mismatch, e.g. `CANCELED` single-L, or the enum was never migrated
to include a cancel-specific value at all). `GET /api/v1/simulations/{id}/status`
immediately after the failed cancel call still showed `running` — the app-level cancel does
NOT reliably stop a job.

**Worked around**, not fixed: confirmed the real underlying AWS Batch job was still
genuinely running via `aws batch describe-jobs`, then terminated it directly via
`aws batch terminate-job --job-id <id> --reason "..."`. The job's own `statusReason` came
back `"cancelled via sms-api"`, suggesting the app's cancel handler DID successfully send a
real cancel signal to AWS Batch before hitting the DB write error — the bug is specifically
in the terminal-status DB write, not the actual cancel dispatch. A subsequent status GET
picked up the real terminal state correctly (viva-api's own polling loop reconciles real AWS
state independently of the broken manual-cancel write path), so the DB doesn't end up
permanently stuck — just transiently wrong, and the cancel ENDPOINT ITSELF still doesn't
work as called. Full detail: [[item35-post-item38-revalidation-pilot]] (memory).

## RETURNED 2026-08-16 — root cause is TWO real bugs, not one; campaign-cancel question answered: NO

**Root cause, confirmed empirically against a real Postgres 15 + this repo's own actual Alembic
migration chain (never `create_all`, which can't catch a migration-shaped defect)**:
`ORMHpcRun.status: Mapped[JobStatusDB]` has no `values_callable`, so SQLAlchemy's default `Enum`
type binds by the Python enum member's **name** (upper-case), not `.value`. The real, migration-
produced `jobstatusdb` Postgres enum never had upper-case `'CANCELLED'` — prior migration
`a1c3e5f7b9d2` added the wrong case (lower-case `'cancelled'`, which the app never writes) — **and
never had `'PENDING'` at all**, despite `DatabaseServiceSQL.list_active_hpcruns`/
`list_active_chain_campaigns` (the chain-campaign poller) both binding `JobStatusDB.PENDING`
against this same column today — a second, already-live failure on the identical root cause, not
hypothetical.

**Fix**: new migration `44335812e447` — `ALTER TYPE jobstatusdb ADD VALUE IF NOT EXISTS 'PENDING'`
/ `'CANCELLED'`. **Bonus same-root-cause fix**: `db_reconcile.py`'s `a1c3e5f7b9d2` fingerprint
marker checked only the lower-case spelling, so it was permanently `False` for any
`create_all`-bootstrapped database — confirmed this **currently misclassifies every fresh
deployment's database as `INCONSISTENT`**, refusing to auto-reconcile. Fixed to accept either
spelling, new marker added for `44335812e447` per this repo's own fingerprint-maintenance contract.

**Tests**: real Postgres 15 (testcontainers) + real Alembic migrations + real
`DatabaseServiceSQL` code — reproduces the exact production error pre-fix, proves the fix
post-fix, including the two `PENDING`-binding queries. All 5 pre-existing `test_cancel.py` tests
still pass unmodified — confirmed they never caught this because they use a `create_all` fixture,
which structurally cannot exercise a migration-history defect (matches this project's own
green-mock-as-go-signal anti-pattern in spirit, though not literally a mock). `make check` clean;

tracing the real code path end to end**: `cancel_simulation` → `SimulationServiceRay.cancel_job`
resolves exactly one `HpcRun.job_id_ext` and terminates exactly that one AWS Batch job. For a

final `insert_hpcrun` call) — never `chain_final_job_ids`, no `dependsOn` walk. ParCa is almost
always already terminal by the time a mid-flight campaign needs cancelling, so this call is very
likely a no-op against an already-finished job while the campaign's real, billed N×G compute keeps
running untouched. **Item 53's walk-back-through-`dependsOn` design remains the real fix for
campaign-wide cancellation** — this PR does not provide it and was not asked to.
