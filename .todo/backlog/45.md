## Goal

Bump sms-ecoli's own `process-bigraph`/`bigraph-schema` floor and lock — in the **sms-ecoli repo**,
not vivarium-workbench — to a version that satisfies vivarium-workbench's declared floor
(`process-bigraph>=1.8.2`, `bigraph-schema>=1.4.3`; `vivarium-workbench/pyproject.toml:26`),
verified via sms-ecoli's OWN test suite passing under the new version first (and a check that
scientific/numerical output is unchanged). This makes the "combined env" vivarium-workbench's
multi-stage Dockerfile assumes — `COPY --from=workspace` sms-ecoli's published `v2ecoli` venv
wholesale, then `uv pip install --no-deps .` to install vivarium-workbench's own package into that
same venv — an actually-enforced contract between both repos' lockfiles, instead of resting on an
unenforced `--no-deps` assumption.

This is option **(c)** from backlog item 44's fix-options list (`.todo/backlog/44.md`), filed here
as its own item per Alex's explicit instruction rather than folded into item 44's immediate
response.

## Why this is needed

Root cause, confirmed live 2026-08-13 (item 44): neither repo installs `process-bigraph` from
PyPI — both pin an exact upstream git commit via `uv.lock`. **sms-ecoli** is locked to commit
`355fa15c...` (= tag `v1.5.0`). **vivarium-workbench**'s own `uv.lock` resolves to `0e65c0c2...`
(= tag `v1.8.2`) — but vivarium-workbench's Dockerfile (item 39's "Fix B") never actually installs
its own lock's version into the shipped image: it `COPY`s sms-ecoli's published `v2ecoli` image's
`.venv` wholesale (built by sms-ecoli's own `uv sync` against sms-ecoli's lock —
`process-bigraph==1.5.0`, `bigraph-schema==1.4.2`), then layers vivarium-workbench's own package
into that SAME venv via `uv pip install --no-deps .`. `--no-deps` means this step never resolves
or enforces vivarium-workbench's declared `>=1.8.2`/`>=1.4.3` floor — the shipped image's actual
`process-bigraph` is whatever sms-ecoli's build put there, silently, regardless of what
vivarium-workbench's own `uv.lock` says.

This exact gap was predicted **in advance** by memory
`workbench-image-process-bigraph-version-floor-risk`, filed during item 39's Fix B design, before
it ever caused a failure. It has since materialized as a real production incident, not a
hypothetical: item 44, the `workbench` Deployment in `sms-api-stanford` (smscdk prod) hit
`CrashLoopBackOff`, live-confirmed 2026-08-13, deterministic crash on every restart:

```
File ".../vivarium_workbench/lib/artifacts/hashing.py", line 24, in <module>
    from process_bigraph.artifacts import (  # noqa: F401
ModuleNotFoundError: No module named 'process_bigraph.artifacts'
```

The `artifacts` submodule was added upstream in process-bigraph commit `cc89f19e` (2026-07-31) —
confirmed an ancestor of `v1.7.1`+ but NOT of `v1.5.0`, i.e. it postdates sms-ecoli's locked commit
by about a month and predates vivarium-workbench's own locked commit. Empirically confirmed (not
just inferred) via a live `kubectl exec` against the crashing pod mid-restart:
```
FILE: /app/v2ecoli/.venv/lib/python3.12/site-packages/process_bigraph/__init__.py
DIST_VERSION: 1.5.0
SUBMODULES: [... no 'artifacts' entry ...]
```

**This item is explicitly NOT item 44's immediate fix.** Item 44 is landing its own narrower,
independent fix — option **(b)**: a surgical, pinned, explicit upgrade of just `process-bigraph`
(and `bigraph-schema` if needed) as its own extra install step in vivarium-workbench's Dockerfile,
low blast radius, restores service this session. This item does not block that work, and that work
does not block this item — they are deliberately decoupled.

The original memory already named the durable fix, quoted directly:

> "The clean way to close this gap for real (not part of item 39's own scope) would be for
> sms-ecoli's `pyproject.toml` to bump its OWN floors on `process-bigraph`/`bigraph-schema` to match
> (or exceed) what it's already actually locked to... making the 'combined env' the Dockerfile's own
> header comment describes an actually-enforced contract between the two repos' lockfiles, not an
> assumption resting on `--no-deps` never being questioned. This is a cross-repo (sms-ecoli +
> vivarium-workbench) design decision, not a unilateral one."

The same memory also flagged a related, narrower open question worth resolving in the same pass:
`pbg-basic-processes` and `viva-marketplace` (both real vivarium-workbench dependencies) are not in
sms-ecoli's lock **at all** (`grep -c` returns 0 for both) — whether the combined image genuinely
needs them present is unconfirmed and should be checked as part of scoping this fix, not assumed.

**Explicitly deferred, not urgent.** Alex's own instruction (2026-08-13, during item 44's incident
response): implement item 44's narrow fix now to restore service, and file this cross-repo
root-cause fix separately "rather than rushing a cross-repo dependency bump under incident
pressure." This item is blocked on nothing (item 44 ships its own fix independently) and blocks
nothing. Landing it requires, at minimum: sms-ecoli's own test suite passing under the bumped
`process-bigraph`/`bigraph-schema`, a check that scientific/numerical output is unchanged, and
likely input from sms-ecoli's other maintainers (Jim, Eran — named co-owners of parts of this
ecosystem per project convention) before merging, since sms-ecoli is the flagship scientific model
repo this whole ecosystem's MVP deliverable depends on. Not to be done unilaterally.
