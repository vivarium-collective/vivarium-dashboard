## Goal

Implement and add sleek, modern, and attractive progress animation(s) to vivarium-workbench for newly opened workspace loading.

## Why this is needed

In the fully remote deployment of vivarium-workbench UI, any time a user selects a workspace (other than the active one),
a new tab opens. That new tab and selected workspace takes enough wall time to produce an uncomfortable UX. As it stands right now,
the only UI feedback that the user receives is static text that says somehting like "Now loading...". It would be great to instead have an 
industry-grade, production-grade, highly sleek/modern UX with some sort of beautiful progress component (progress bar would be cool, but only if
we could introspect into the iterative state of this loading, so if not progress bar, maybe spinner or reactive svg?)

## Investigation update (2026-08-13)

Grounded, evidence-based plan from a source-verified investigation (two independent agents,
cross-checked against the real code, not assumed):

**Verified render sequence.** New tab opens via `window.open(bp + "/?build=" + simulator_id)`
(`static/workspace-picker.js:161-163`). First paint is wrong by construction: `GET /`
(`index_shell`, `app.py:3639-3671`) resolves the workspace purely from the session
cookie/header and never reads `?build=` at all — the query param is inert until JS acts on
it. `session.js`'s `bootstrapSpawn()` (`119-163`) then POSTs `/api/source/switch-build`,
which does real, non-trivial work: a per-session `shutil.copytree`
(`lib/remote_build_source.py:152-221`) plus 5 sequential git subprocesses
(`remote_build_source.py:224-270`). No hardcoded delay exists anywhere in this path — the
~10s is organic latency from that real work (cold path is documented at ~224s,
`remote_build_source.py:39`, so a warm cache still costs real seconds). On success,
`session.js` strips the URL param (`138-145`) then does a full `window.location.reload()`
(`153-157`).

**Reusable patterns already in this codebase** (per this repo's own "extend before
inventing" convention): `.modal-overlay`/`.modal-box` (`templates/index.html.j2:35-71`,
already used 13× elsewhere), `.ptrack-spin` keyframes (`static/progress-track.css:47-60`,
already reduced-motion-aware), and `session-status.js`'s existing "materializing"
favicon/title poll + `renderFailure()` panel pattern (`63-79`, `109-161`) — currently scoped
only to the favicon, not full page chrome.

**Proposed mechanism**: extend the same technique this codebase already uses to prevent a
dark-theme flash (a synchronous, pre-paint inline `<script>` in `<head>`,
`index.html.j2:6-7`) — add one more: when `location.search` carries `build=`/`workspace=`,
stamp a `data-ws-boot` attribute before first paint; CSS hides the (wrong) workspace name
and shows a full-page overlay reusing the existing `.modal-overlay` + `.ptrack-spin`
("Opening workspace…", optionally naming the real target via `ws.label`, already available
in `openWs()` at `workspace-picker.js:68-70`). Dismissal: the success path needs nothing
extra (the reload replaces the DOM); the currently-silent `.catch()`
(`session.js:158-162`, today stranding the user on failure) should dismiss the overlay and
show a real error via `session-status.js`'s existing `renderFailure()` pattern instead.

**Complexity: small.** Files: `templates/index.html.j2` + `static/session.js` only.
**Frontend-only** — no backend/cookie-mechanism changes needed for this item specifically.

**See also item 48** (persistent-build-URL architecture + a real cross-tab cookie-clobbering
correctness bug found during the same investigation) — a related but distinct, more
architectural angle on the same underlying transition. The binding-placeholder state item 48
proposes for `index_shell` is the same surface this item's loading animation would render
into, so the two are worth implementing together rather than independently, even though
either can ship alone.
