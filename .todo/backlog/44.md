## Goal

Get the `workbench` Deployment in `sms-api-stanford` (smscdk prod) back to a healthy, serving
state. It is currently in `CrashLoopBackOff` — 0/1 available — confirmed live 2026-08-13.

## Why this is needed

**Found 2026-08-13**, while re-verifying backlog item 39's own live registry fix via a fresh
`/goal` session. `kubectl get pods -n sms-api-stanford -l app=vivarium-workbench` shows pod
`workbench-6584c98b9f-87jqw`, `0/1 CrashLoopBackOff`, 30 restarts over ~142 minutes. Both the
`workbench` main container and the `seed-workspace` init container are correctly pinned to
`ghcr.io/vivarium-collective/vivarium-workbench:0.3.41` — the deploy itself landed as intended,
this is not a deploy-config bug; the running image is exactly what was intended.

`kubectl logs --previous` shows a deterministic crash on every restart, ~16 seconds after start,
always the identical traceback:

```
File ".../vivarium_workbench/lib/artifacts/hashing.py", line 24, in <module>
    from process_bigraph.artifacts import (  # noqa: F401
ModuleNotFoundError: No module named 'process_bigraph.artifacts'
```

This fires at server *import* time (`vivarium_workbench.api.app` → `investigation_resolve_views`
→ `artifacts/pipeline.py` → `artifacts/hashing.py`), before the FastAPI app object even exists —
so literally nothing is served. `api` and `ptools` (siblings in the same namespace) are unaffected
and healthy; this is isolated to the `workbench` Deployment.

**Leading hypothesis, well-evidenced but NOT yet fully confirmed**: memory
`workbench-image-process-bigraph-version-floor-risk` (filed earlier in the same item-39 session
that produced this deploy) already flagged, in advance, that `vivarium-workbench/pyproject.toml`
declares `process-bigraph>=1.8.2`, but sms-ecoli's actual locked version is `1.5.0` — and that item
39's Fix B (multi-stage Dockerfile, `COPY --from=workspace` the sms-ecoli-published `v2ecoli` venv
wholesale, `uv pip install --no-deps .` for the workbench's own install on top) deliberately never
enforces that floor, to avoid a *different*, worse version-skew risk (see that memory for the full
reasoning). `vivarium_workbench/lib/artifacts/hashing.py` importing `process_bigraph.artifacts` at
module load time is consistent with vivarium-workbench code assuming a `process-bigraph` feature
that the actual installed 1.5.0 doesn't have.

**What's NOT yet confirmed, and must be before writing any fix**:
1. That `process-bigraph` 1.5.0 genuinely lacks an `artifacts` submodule while some version
   `>=1.8.2` has it (check installed version directly, check process-bigraph's own history/CHANGELOG).
2. **Why 0.3.40 booted clean** (live-exec-verified healthy earlier this same saga) if 0.3.41 crashes
   on the same underlying dependency gap — both AWS Batch builds *appear* to have targeted the same
   `WORKSPACE_IMAGE` (`v2ecoli:8d50ff0`) per prior session notes, which would predict IDENTICAL
   `process-bigraph` versions in both. Two unexplained variables sit between the 0.3.40 and 0.3.41
   tags: item 39's own PR #799 (`build_analysis_options` plural-import fix — touches unrelated code,
   shouldn't affect startup imports) AND an unrelated PR #796 ("chore: consolidate agents/0 +
   track-colors + tally duplication") that also landed in that same window. Do not assume either
   explanation without checking git blame on `vivarium_workbench/lib/artifacts/hashing.py` and the
   two AWS Batch jobs' actual build parameters directly.

**This blocks item 39's own remaining verification** (`.todo/backlog/39.md`) — the live
`ANALYSIS_REGISTRY` count can't be checked at all right now, `kubectl exec` fails because the
container never stays up long enough. Also blocks all real UI-only dispatch work and, more
immediately, blocks the workbench from serving ANY traffic to anyone right now.

4 of 5 investigation agents back, all pointing at the same conclusion:

- **Not new code**: `git diff` between the healthy 0.3.40 tag commit and the crashing 0.3.41 tag

- **The real mechanism, very high confidence**: neither this repo nor sms-ecoli installs
  `process-bigraph` from PyPI — both pin an exact upstream git commit via `uv.lock`. sms-ecoli is
  locked to `355fa15c...` (= tag `v1.5.0`, confirmed via direct GitHub file listing: no

- **Why this matters**: this repo's own multi-stage Dockerfile (item 39's own "Fix B") does `COPY
  --from=workspace /app/v2ecoli/.venv ...` (the WORKSPACE_IMAGE's venv, built by SMS-ECOLI's OWN

  vivarium-workbench's own package into that SAME venv via `uv pip install --no-deps .`.
  `--no-deps` means this step never resolves or enforces vivarium-workbench's own declared
  `>=1.8.2` floor — the shipped image's actual `process-bigraph` is whatever sms-ecoli's build put
  there, independent of what vivarium-workbench's own `uv.lock` says. This exact risk was already
  flagged in advance by memory `workbench-image-process-bigraph-version-floor-risk`, filed earlier
  in the same session that designed Fix B — the predicted failure mode has now materialized as a
  real crash, not a hypothetical.
- **Likely NOT actually new to 0.3.41**: if this mechanism is right, the crash has been present
  since Fix B first shipped (0.3.39/0.3.40) — the earlier "0.3.40 confirmed healthy" check in this
  saga was a single `kubectl exec python -c "..."` one-liner, which only needs the container to be
  briefly `Running` (the same narrow window a crash-looping container passes through every restart
  cycle), never cross-checked against pod restart count. The 0.3.40 ReplicaSet no longer exists to
  re-verify this directly.
