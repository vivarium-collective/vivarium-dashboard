# Q1/Q2 comprehensive synthesis — workspace-picker UI gap, and unifying dispatch parameterization

Written 2026-08-13, synthesizing three independent research/design passes: Q1 (workspace-picker
all-versions selector), Q2.1 (parameterizable composite dispatch), Q2.2 (ecoli-sources ParCa
parameterization). Q2.1 and Q2.2 were run concurrently and explicitly asked to converge into one
proposal — the cross-connection between them below is the actual point of running them together,
not something either agent could see on its own.

Status: pure research + design, nothing implemented, nothing committed. This document itself is a
proposal for review, not a change log.

---

## The headline finding: Q2.1 and Q2.2 share one root cause

Both investigations independently found the exact same shape of problem: **the parameterization
mechanism recalled from history already exists in viva-api's code — twice — but both times it's
wired to the wrong backend.**

- **Composite/config (Q2.1)**: the historical vEcoli-private JSON-config-as-request-body paradigm
  isn't just history — `run_simulation_workflow` (`viva_api/common/handlers/simulations.py:465-651`)
  still executes it, verbatim, today, for the SLURM and K8s+Nextflow(vEcoli) backends. The RAY
  backend — what sms-ecoli/v2ecoli's canonical `batch_baseline` dispatch actually uses — explicitly
  opts out of this whole mechanism (its own code comment: *"v2ecoli (RAY) has no configs/ dir and
  runs from CLI args... the Nextflow/AWS config blocks are unused"*) and instead uses a different,
  process-bigraph-native `composite_id + overrides` system. That system is already generic and
  already works — it just isn't exposed to any request field.
- **ecoli-sources (Q2.2)**: viva-api already built a complete, production-grade sync mechanism for
  this — GitHub repo → S3 → container env var injection, with real security hardening (org
  allowlist, path-traversal protection, size caps, its own test suite,
  `viva_api/common/handlers/simulations.py:157-241`). It's wired into `simulation_service_k8s.py`
  (the BATCH backend) only. `simulation_service_ray.py` — the file that dispatches every real
  sms-ecoli/v2ecoli simulation — has **zero references** to it.

Same story, twice: when the ecosystem migrated its canonical dispatch from the old
Nextflow/SLURM-based backend to the new Ray/AWS-Batch-MNP-based backend (the items 33/34/35
chain-dispatch rework), two pre-existing, working parameterization mechanisms got left behind on the
old backend and never ported to the new one. The fix isn't "invent new parameterization" — it's
"finish a port that stalled halfway."

Both agents also flagged, independently, that they're touching **the exact same three files**
(`viva_api/api/routers/sms.py`, `viva_api/common/handlers/simulations.py`,
`viva_api/simulation/simulation_service_ray.py` / `models.py`) — this should land as one bundled
change, not two separate PRs, per this repo's own BOJ tenet 1 (one PR, bundled).

## Q1 — workspace-picker all-versions selector

### The verified premise correction

The starting claim was "local mode already shows a by-row-selectable all-versions list." Checked
directly against `workspace-picker.js` and `lib/workspace_deps_views.py:build_workspaces()`
(125-251): local rows come from the global catalog `~/.pbg/workspaces.json`, one row per
**filesystem checkout currently on disk** — multiple rows for the same repo only appear if there are
literally multiple clones/worktrees. This is enumeration of directories, re-derived live via `git`
shell-outs, not a commit/version history browser. A "version" here means "whatever a directory's
HEAD happens to be right now" (mutable) — a structurally different concept from a remote row, which
is an immutable registered `repo@commit` build.

The corrected framing: local mode was never doing "all versions by row" — remote's underlying data
is actually the *better* fit for a real history browser (see below), the client is just discarding
it.

### Why the existing "#github" page is the wrong home

`branch-source.js`, routed at `#github` (`index.html.j2:452`), does four unrelated jobs in one
panel:

1. Scope toggle (Local/Remote) + a live health-probe dot for the sms-api tunnel connection.
2. A cascading 3-level drill-down: Repo select → Branch select → Commit select (only appears once
   &gt;1 build shares a branch) — picking a repo **collapses away every other repo**.
3. Five action buttons of mixed purpose sharing one row: "Open" (navigation), "Commit + Push"
   (mutates local git), "Build via sms-api" (registers a brand-new build), "Sync to local" (prints a
   CLI command).
4. The actual flat list (438-471) — structurally closest to what's wanted — is pre-scoped to the
   currently-selected repo+branch by default; its search box only renders conditionally
   (`if (matches.length &gt; 1 || (state.filter||"").trim())`, line 429), and even widened, results stay
   repo-scoped for remote (`pool = (state.scope === "remote") ? inRepo : state.entries`, line 446).

This is an information-architecture mismatch, not just clutter — a repo-administration console with
a picker grafted in, rather than a picker with administration nearby.

### What already exists to reuse

Three independently-built "sleek row list" components already share one visual language
(`#e2e8f0` borders, `#f1f5f9`/`#f6f8fa` hover states, indigo current-row highlight, ellipsis
truncation, hover-reveal secondary actions):

| Component | CSS family | Location | Notable feature |
|---|---|---|---|
| Workspace-picker dropdown | `.viv-wsp-*` | `index.html.j2:213-265`, `workspace-picker.js:191-273` | search-filter box, pin toggle, hover-reveal per-row actions |
| Branch-source list | `.viv-bs-*` | `index.html.j2:455-498`, `branch-source.js:438-471` | current-row highlight, per-row "forget" |
| Investigation switcher | `.viv-iset-menu-*` | `index.html.j2:412-571`, `investigation-switcher.js` | labeled section headers + dividers, hidden when empty — already solves "many rows across several logical groups" |

A fourth, centered-modal variant (`workspace-switcher.js`) was built earlier and is confirmed dead —
`index.html.j2:2120-2123` states it explicitly: "the left-rail dropdown it used to drive has been
repurposed into the investigation switcher." Every currently-*live* pattern is an anchored/rail-
relative panel, not a centered overlay — worth knowing before proposing a new shape.

**Backend data is already complete and already in the browser.** `GET /api/source/builds`
(`api/app.py:3071-3086` → `lib/remote_build_source.py:list_build_sources()`, 273-297) returns every
registered build with every field a table needs — `{simulator_id, repo, repo_url, commit, branch,
created_at, label}` — fetched fresh on *every* dropdown open (`workspace-picker.js:337`) and
immediately discarded by `normalizeRemoteBuilds()`. **No new endpoint, no new proxy, no new data —
this is a pure client-side discard problem.**

Build registration dedups by commit (`POST /core/v1/simulator/upload`,
`viva_api/api/routers/core.py:148-176` — an existing version short-circuits unless `force=True`), so
list length tracks "how many distinct commits someone explicitly built," not "how many simulations
ran." Realistic per-repo counts stay in the tens over a project's life — comfortably within what a
searchable row list handles.

### Three options, waterfall-scored

**Item: browse/select any historical build, not just latest.**
1. *Existing pattern usable out of the box?* Close — the row-rendering technique is generic over any
   array shape, but no call site exists that doesn't pre-reduce the data first. Falls just short.
2. *Existing pattern extendable?* **Yes** — two direct extension points (the picker's own row/list
   machinery, or the investigation-switcher's proven section-header/hide-when-empty grouping
   pattern). **Stop here.**
3-4. Not reached.

- **Option A — un-reduce the existing dropdown itself.** Smallest effort, but fights the control's
  own stated design goal ("get me into a repo quickly") and reintroduces the same "too much in one
  surface" complaint one level down.
- **Option B — dedicated flyout panel, contextually triggered (recommended).** Keep the fast default
  dropdown's latest-only reduction untouched; tally a per-repo build count while already iterating;
  when &gt;1 exists, show a "+N more" affix or footer "All builds…" link (mirroring the existing
  "Branch settings ↗" link at line 311) that opens a small anchored panel — same fixed-position
  technique the dropdown already uses — listing every build, reusing the row DOM/CSS verbatim.
  Estimated ~100-150 lines JS (mostly an extracted shared row-builder) + ~40-60 lines CSS adapted
  from `.viv-wsp-menu`/`.viv-wsp-list`. **Zero backend changes.**
- **Option C — restructure `branch-source.js` in place.** Smallest of all three, but doesn't
  address the actual complaint — still the page explicitly called out as the wrong home. Not
  recommended.

**Recommendation: Option B.** One honestly-flagged gap: pinning (`_wsPins()`) keys remote rows by
`"remote:" + repo`, not commit — pinning an individual *older* build isn't representable in today's
data model. Recommend view-and-open-only for the new panel in v1, not extending pin semantics as a
side effect (keeps the diff minimal).

## Q2.1 — parameterizable composite dispatch

### The historical framing, verified point by point

**`vEcoli-private/runscripts/workflow.py` — confirmed, more precisely than remembered.** It's not an
HTTP client of any viva-api-family endpoint — it's a standalone CLI that loads `--config
&lt;path.json&gt;` via `load_config_with_inheritance()` and either runs Nextflow locally or submits via
`sbatch`. The real, current schema (`vEcoli-private/configs/api_simulation_default.json`) contains
exactly the "canonical" fields remembered: `experiment_id`, `parca_options`, `generations`,
`n_init_sims`, `analysis_options.multiseed` (containing `cd1_higher_order_properties`,
`cd1_transcriptomics`, `cd1_proteomics`, `cd1_metabolomics`, `cd1_fluxomics`, `ptools_rxns`,
`ptools_rna`, `ptools_proteins` — the deliverable's own artifact set), etc. So the "request body" role
was always played one layer up from `workflow.py` itself, by whatever wraps it.

**Is this still live, or superseded? Confirmed still live, not past tense.** `run_simulation_workflow`
(`handlers/simulations.py:465-651`) still executes exactly this paradigm today for SLURM/K8s+Nextflow:
reads the config template, string-replaces placeholder tokens (`EXPERIMENT_ID_PLACEHOLDER` etc. —
literally visible unfilled in the vEcoli-private config file itself), applies a fixed override
whitelist, wraps the result in `SimulationConfig(**config_data)`. `SimulationConfig`
(`viva_api/simulation/models.py:218-297`) even has ~50 fields **commented out** that field-for-field
match this exact schema — direct textual evidence the model was once fully declared against it.
**Critical qualifier, confirmed in the same function**: the RAY backend explicitly opts out —
*"v2ecoli (RAY) has no configs/ dir and runs from CLI args... the Nextflow/AWS config blocks are
unused."*

**Was the pattern ported into v2? Confirmed yes — but into a different, disconnected path.**
`sms-ecoli/v2ecoli/workflow/config.py` opens with *"Ported from vEcoli
runscripts/workflow.py:load_config_with_inheritance"* — a faithful, tested port. But its only
consumers are `v2ecoli/workflow/run.py`, a separate CLI entrypoint architecturally parallel to, and
disconnected from, the `batch_baseline` composite. `simulation_service_ray.py`'s dispatch code never
imports or shells out to it — it only invokes `run_pbg.py --composite-id ... --overrides ...`.

So there are, right now, **two live, independently-real "config paradigms"** in sms-ecoli, and
viva-api's canonical AWS dispatch uses the one that was never wired to a request field:

| Mechanism | Where | Ported from vEcoli-private? | Used by viva-api's canonical (RAY) dispatch? |
|---|---|---|---|
| JSON file + `inherit_from` chains | `v2ecoli/workflow/config.py` + `run.py` | Yes, verbatim | **No** |
| `composite_generator(parameters={...})` + `overrides` dict | `v2ecoli/composites/batch_baseline.py` + `process_bigraph.composite_spec` | No — process-bigraph-native | **Yes** |

### viva-api's real current endpoint surface

Confirmed via `viva_api/common/gateway/utils.py:17-25` and `viva_api/common/utils.py:18`
(`CURRENT_API_VERSION = "v1"`): the "sms" router mounts at `/api/v1`, the compose router at
`/compose/v1` (sibling prefixes, not nested — corrects the "maybe `/api/v1/compose`" guess).

**`/api/v1` (`viva_api/api/routers/sms.py`) — the live dispatch surface:**

| Method | Path | Purpose |
|---|---|---|
| POST | `/simulations` | **The real dispatch endpoint** (`run-ecoli-simulation-new`, sms.py:184-304) |
| GET | `/simulations/{id}`, `/status`, `/simulations` | status/list |
| DELETE | `/simulations/{id}/cancel` | cancel |
| POST | `/simulations/{id}/analysis` | on-demand analysis re-run |
| GET/POST | `/analyses`, `/analyses/{id}/*` | analysis job surface |

**`/compose/v1` (`viva_api/api/routers/compose.py`) — a separate lineage, not batch_baseline-wired:**
generic upload-file-based compose run, a narrow `/curated/ecoli` Query-param endpoint that Jinja-
templates a *different* (non-batch_baseline) document, plus unrelated curated-model endpoints
(`copasi`, `tellurium`, `biomodels`).

**Confirmed: no live HTTP endpoint anywhere accepts a client-supplied `composite_id` today**
(`grep -rn "composite_id" viva_api/api/ viva_api/compose/*.py` — zero hits outside `run_pbg.py`
itself, server-side-only). The dispatch endpoint's request shape is already a hybrid — a long list of
flat `Query(...)` params, plus **one plain Pydantic-model body parameter**,
`analysis_options: AnalysisOptions | None = None` (line 261, not wrapped in `Query()`). This is the
load-bearing precedent for the design below.

### process-bigraph Composite-spec: confirmed, with one correction

Read `process_bigraph/composite_spec.py` (installed, `1.5.0`) directly. A registered `CompositeSpec`
carries `parameters: dict` — `{name: {type, default, description, choices?}}` — and
`to_document(overrides, core)` merges overrides over declared defaults, raising on unknown keys.
`batch_baseline` declares exactly **17 parameters** — so "a flattened dict of otherwise-nested
configurable attributes" is precisely what `overrides` already is, structurally, today.
`variants: {"type": "map", "default": {}}` is already a dict-shaped slot for exactly this purpose.

**Correction to the original task framing**: the earlier assumption was "raises `ValueError` on
unknown keys." Reading the code directly: `composite_spec.py:202`'s `_merged_params` raises
**`KeyError`**, not `ValueError`. A `ValueError`-wrapping layer does exist
(`pbg_superpowers/composite_generator.py:435-468`'s `build_generator()`) but `run_pbg.py:169-183`
(the function viva-api's Ray dispatch actually executes) calls `to_document()` directly, bypassing
that wrapper. **So on the real dispatch path, an unknown override key raises a bare, uncaught
`KeyError` inside an already-running, already-billing Batch container — after ParCa has already
completed.** A concrete, material argument for API-layer validation, not just a nice-to-have.

`run_pbg.py`'s own docstring states the design intent this whole proposal is completing, verbatim:
*"This is what lets a model-specific dispatcher... submit a config-driven run through the exact same
execution mechanism a hand-authored `.pbg` document uses, instead of shelling out to a bespoke
per-workspace CLI script."* The mechanism was built for exactly this — it just isn't wired to a
client-facing field yet.

### What's reachable today vs. silently fixed

Of `batch_baseline`'s 17 parameters, `_seed_generation_command`
(`simulation_service_ray.py:601-679`) sets:

- **Server-computed, correctness-critical, must stay fixed**: `cache_dir`, `out_dir`, `analyses`
  (hardcoded `"none"` — deliberately deferred to a separate DAG node), `parallel`, `base_seed`,
  `initial_generation_index`, `initial_carry_state_path`, `daughter_state_out_path` (S3 layout /
  checkpoint-resume chain correctness).
- **Client-influenced today**: `n_seeds`/`n_generations` (via campaign-level Query params),
  `experiment_id`.
- **Never touched by viva-api at all — always the composite's hardcoded default, regardless of what
  any study/client configures**: `single_daughters` (always `True`), `time_step` (always `1.0`),
  `max_duration` (always `3600.0` — note: vEcoli-private's own canonical default is `10800.0`, a 3x
  mismatch, independent finding, worth a look on its own), `variants` (always `{}`), `emitter`
  (always `"both"`), `study` (always `""`).

**6 of 17 real biological/simulator-specific parameters are currently unreachable from any request**,
and `variants` — structurally the closest thing to "flattened configurable dict" — is one of them.

### The concrete design proposal

Run through the mandatory waterfall:
1. *Existing pattern usable out of the box?* Partially — `run_pbg.py` + `composite_spec.to_document
   (overrides=...)` is already a fully generic, working, `composite_id`-agnostic override mechanism.
   **Nothing there needs to change.**
2. *Extendable, no new concept?* Yes — `SimulationConfig` is already `extra="allow"`; the endpoint
   already mixes flat Query overrides with one structured JSON-body sub-model (`analysis_options`).
3. *Battle-tested framework instead?* N/A at this scope — FastAPI/Pydantic is already the framework
   in use; nothing new is being introduced.
4. *Minimal satisfiable design*:

```python
# viva_api/simulation/models.py, sibling to AnalysisOptions
class BatchBaselineOverrides(BaseModel):
    model_config = ConfigDict(extra="forbid")   # reject unknown fields with a clean 422
                                                  # at the API boundary, before any Batch spend
    single_daughters: bool | None = None
    time_step: float | None = Field(default=None, gt=0)
    max_duration: float | None = Field(default=None, gt=0)
    variants: dict[str, Any] | None = None
    emitter: Literal["both", "parquet", "xarray"] | None = None
```

`study` and the 8 server-owned keys are structurally absent from this model, not just defaulted — a
caller cannot supply them even by trying.

- `sms.py:261` — add `composite_overrides: BatchBaselineOverrides | None = None` next to
  `analysis_options`.
- `handlers/simulations.py` — thread it through; reject with a 400 if the resolved backend isn't
  RAY (an explicit rejection is a better failure mode than a silent no-op).
- `simulation_service_ray.py` — merge as `overrides = {**client_overrides,
  **server_computed_overrides}`. **This dict-merge ordering is the actual safety mechanism**, not the
  Pydantic model alone — server-computed keys win even if the allowlist model is ever loosened later.
  Worth stating explicitly in the code, not just this doc.
- Optional, separate: promote the hardcoded `V2ECOLI_BATCH_BASELINE_COMPOSITE_ID` into a `Settings`
  field (mirroring `settings.ray_ecr_repository`), **not** a per-request client field — the whole
  downstream DAG (S3 layout, checkpoint/resume key names, the analysis node's parquet-output
  assumption) is written against `batch_baseline`'s specific contract; a client-swappable composite
  id would silently break for anything that doesn't share those exact parameter names. Deploy-time,
  not request-time.

**Sizing**: ~5 files in viva-api (`models.py`, `sms.py`, `handlers/simulations.py`,
`simulation_service_ray.py`, optionally `config.py`). No new services, no new endpoints, no
process-bigraph/pbg-superpowers/sms-ecoli changes — every extension point already exists.

**Explicitly out of scope**: `vivarium-workbench`'s `remote_run_submit` doesn't even forward the
already-existing `composite`/`variants`-adjacent fields today — a UI path to set
`composite_overrides` from a Study spec is a real, separate follow-up, not sized here.

## Q2.2 — ecoli-sources / ParCa parameterization

### What it is, confirmed against the live UI

`ecoli-sources` (`vivarium-collective/ecoli-sources`) is a real, git-pinned dependency
(`sms-ecoli/pyproject.toml:151`, pinned to a specific commit). Installed, it ships a 135-row manifest
(`ecoli_sources/data/reference_bundle.tsv`, `canonical_key → source_path`) plus a `data/flat/` tree
across ten subdirectories — an exact match to the live workbench UI's "ecoli-sources (135 files, 4
overrides)" panel and its listed subdirectory names.

The resolver is `SourceBundle` (`v2ecoli/processes/parca/reconstruction/ecoli/sources.py`, ported
from CovertLab/vEcoli PR #426), which layers a local override manifest on top of the base one.
`KnowledgeBaseEcoli` accepts an optional `bundle=` param; ParCa's CLI always constructs and passes
one.

### The "4 overrides" — resolved, and a stale-docs bug found along the way

Live `parca_overrides.tsv` genuinely has 4 rows (`equilibrium_reactions`,
`equilibrium_reaction_rates`, `metabolic_reactions_added`, and an undocumented 4th, `dna_sites`).
`sms-ecoli/docs/parca_data_bundle.md` still says "three files" — written in one commit and never
updated after `dna_sites` was added. The live UI's "4" is correct; the doc is stale. Small, concrete,
easy fix, found as a side effect of this investigation.

Separately notable: sms-ecoli and v2ecoli pin **different** ecoli-sources commits — a real divergence
between the two trees worth knowing about.

### Today's dispatch-time reality

Locally, exactly one real parameter exists: `v2ecoli-parca --bundle-manifest-path &lt;path&gt;` replaces
the base manifest (the 4-row override layer always applies on top regardless) — a CLI flag, not a
dispatch-API field.

**viva-api already built the dispatch-time mechanism — it just doesn't reach the path that matters.**
`POST /api/v1/simulations` exposes `ecoli_sources_uri`, `ecoli_sources_overlays`,
`ecoli_sources_repo_url`, `ecoli_sources_ref`. Server-side, `_sync_ecoli_sources_from_github()`
(`handlers/simulations.py:157-241`) downloads a GitHub tarball, enforces an org allowlist
(`vivarium-collective`, `CovertLab`, `CovertLabEcoli`), validates a manifest, rejects path traversal,
caps file count/size, uploads to S3 — genuinely production-grade, with its own test file covering all
of it. The resulting URI is injected as container env vars — **but only in
`simulation_service_k8s.py:281-286`**.

`ComputeBackend` has three members: `SLURM` (UCONN CCAM), `BATCH` (AWS Batch via Nextflow —
vEcoli-fork/public/private repos), `RAY` (AWS Batch MNP transient Ray cluster — v2ecoli AND
sms-ecoli, explicitly mapped in `config.py`). `simulation_service_ray.py` (1471 lines, the actual
class dispatched for sms-ecoli) has **zero references** to `ecoli_sources`. It's also unconsumed on
the BATCH side — vEcoli-private (what BATCH's Nextflow path actually runs) has zero references
either, since it predates the ecoli-sources migration entirely. **This plumbing is currently dead on
every backend/repo combination in the ecosystem today.**

**A second, independent bug in the same mechanism**: its manifest validator checks for
`data/manifest.tsv` with columns `dataset_id`/`file_path`. The real ecoli-sources package's manifest
is `ecoli_sources/data/reference_bundle.tsv` with columns `canonical_key`/`source_path`/
`description`/`schema_name`. Even if wired to RAY, it would reject a real ecoli-sources checkout's
actual layout as-is.

### Historical paradigm shift

**Old (vEcoli-private, pre-migration)**: flat files vendored directly in-repo, loaded via hardcoded
filename lists — no manifest, no canonical keys, no external package. Violacein and mecillinam were
each parameterized through repo-specific JSON workflow configs driving Nextflow **simulation-level**
variants (induction time, concentration, knockouts) plus hand-added curated flat files. Even then,
antibiotic/pathway experiments were primarily driven by new process code + simulation-time variant
config layered on top of ParCa — not by swapping ParCa's raw input files.

**Current**: a 2026-06-06 design replaced ~130 of 133 vendored flat files with the shared
`ecoli-sources` package, keeping only the (now 4) v2ecoli-diverged files as a local override layer.
That same design doc sketched a "PR 2 — multi-ParCa runner" with a `parca_variants` config key as the
intended mechanism for per-experiment ParCa input variation. **Confirmed: PR 2 was never built** — a
full-repo grep for `parca_variants` returns nothing.

### The finding that matters most for vio/mec — a verified no-op, tracked as an open issue

- **No mecillinam/violacein pathway data exists in ecoli-sources.** A full-package grep found exactly
  one incidental hit — `metabolites.tsv` lists `"mecillinam"` as a generic compound-catalog row
  (SMILES, molecular weight only) — no dosing, kinetics, IC50, or knockout data, unlike vEcoli-
  private's dedicated per-drug CSVs. Zero hits for "violacein" anywhere.
- **v2ecoli's own report code documents the deeper gap explicitly, with a tracked issue.**
  `sms-ecoli/reports/ecoli_sources_report.py:726-737` (rendered on the `showcase-1-parca` study
  report): *"Input-dataset swaps... require v2ecoli to adopt the bundle's `rnaseq_experimental_tpms`
  abstraction. v2ecoli's ParCa currently fits the legacy wide-format input, so swapping that key is a
  no-op here (**verified: identical fitted expression**). The variant shown below is a ParCa
  configuration variant (operons on/off), which v2ecoli does respond to. Per-condition input swaps
  land with #130."* — the codebase has already tried and verified that swapping bundle data doesn't
  change ParCa's output today. The only proven-working variation dimension is a config flag, not
  data.
- **No violacein-producer simulation exists at all** — `workspace/studies/cd1_ginkgo_viom5_m9/
  study.yaml` grades the wild-type baseline against violacein-producer *measured* data, with an
  explicit caveat that no producer sim exists yet.

**Practical implication**: today's mechanism does not support per-experiment ecoli-sources
variation for vio/mec, and this is already flagged in-repo as open (issue #130), not a gap this
investigation is newly discovering. Wiring the plumbing (below) would not, by itself, unlock
meaningfully different vio/mec ParCa runs — that also needs v2ecoli's own #130 fix and real
biological data curation for those two conditions.

### A secondary correctness risk if this becomes parameterizable

`v2ecoli/library/cache_version.py`'s `INPUT_FILES` fingerprint (11 hardcoded paths) does not include
ecoli-sources bundle/override content. Per existing project knowledge, the ParCa cache is keyed
purely by simulator git commit hash — safe today only because ecoli-sources' commit is transitively
frozen by `uv.lock` at that simulator commit. **If ecoli-sources becomes independently
dispatch-time-parameterizable, this breaks**: two dispatches on the same simulator commit but
different requested ecoli-sources ref/overrides would collide on the same cache key and silently
serve the wrong `sim_data`. Any real implementation must fold the resolved bundle+overrides hash into
the cache key, not just the commit.

### The reusable shape (already exists, just needs the right backend)

```
ecoli_sources_repo_url : str | None   # GitHub URL, org-allowlisted server-side
ecoli_sources_ref      : str | None   # branch/tag/commit, default "main"
ecoli_sources_uri      : str | None   # direct S3 URI (bypass)
ecoli_sources_overlays : str | None   # semicolon-separated overlay manifest URIs
```
Already flows structurally through `SimulationConfig` (`extra="allow"`) and is backend-agnostic at
the pydantic layer today — the gap is purely that `simulation_service_ray.py` never reads it.

## The unified plan

Both investigations converge on the same conclusion, and Q2.1's own report flagged this explicitly:
`ecoli_sources_*` are **already Query params on the exact same `POST /api/v1/simulations` route**,
flowing through the exact same handler and config model that `composite_overrides` would extend.
**This should land as one bundled change to the same ~3 files**, not two separate PRs touching
overlapping code, with both new nested objects following the same `extra="forbid"` +
explicit-typed-field convention (matching the precedent `analysis_options` already sets).

**What the bundled fix would actually do:**
1. Add `composite_overrides` (Q2.1's design) as a new typed body param on `POST /api/v1/simulations`.
2. Port/fix the existing ecoli-sources sync mechanism into `simulation_service_ray.py` (currently
   absent) and correct its manifest-schema validator to match ecoli-sources' real column names.
3. Both mechanisms merge client-supplied overrides with server-computed values via the same
   dict-merge-ordering safety pattern, so server-owned correctness-critical fields can never be
   overridden regardless of what the request contains.

**What it would NOT do, and shouldn't be expected to**: make violacein/mecillinam ParCa
parameterization scientifically meaningful. That's gated on v2ecoli's own tracked issue #130
(`KnowledgeBaseEcoli` actually responding to swapped bundle data, not just a config flag) plus real
biological data curation — genuinely separate, larger, differently-owned work from the API-plumbing
fix above.

### Practical sizing, if acted on

- **The viva-api wiring half** (composite_overrides + ecoli-sources-on-RAY + the manifest-schema
  fix): a real, contained, well-scoped fix. ~5 files, no new services/endpoints, no changes needed
  in process-bigraph/pbg-superpowers/sms-ecoli. Worth its own backlog item.
- **The "make vio/mec actually work" half**: bigger, separate, different owner (v2ecoli-side
  biological code + data curation, not viva-api plumbing). Should not be folded into the same item as
  the wiring fix.
- **Q1's workspace-picker fix**: fully independent of both Q2 threads — a small, self-contained
  frontend change, zero backend involvement, worth its own item too.

None of the above is blocking or part of backlog item 35's own scope.
